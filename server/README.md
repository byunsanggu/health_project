# 서버 붙이기

앱은 이미 **서버 없이 완전히 돌아갑니다.** 서버는 "같은 사람의 다른 기기"를 잇는 역할만 합니다 —
폰을 바꿔도 기록이 남고, 나중에 트레이너 모드가 붙습니다.

그래서 서버가 죽어도 앱은 멈추지 않습니다. 로컬에 먼저 쓰고, 보낼 것을 아웃박스에 쌓아
두었다가 연결되면 흘려보냅니다.

---

## 1. 관장님이 하실 것 (15분)

### ① Supabase 계정 만들기

https://supabase.com → **Start your project** → GitHub 또는 이메일로 가입. 카드 필요 없습니다.

### ② 프로젝트 만들기 — **리전을 꼭 Seoul로**

**New project** 누르고,

| 칸 | 넣을 값 |
|---|---|
| Name | `volume-coach` |
| Database Password | **길게 아무거나. 어딘가에 적어 두세요** — 다시 못 봅니다 |
| Region | **Northeast Asia (Seoul)** ← 이게 제일 중요합니다 |
| Plan | Free |

리전을 잘못 고르면 나중에 못 바꿉니다. 프로젝트를 새로 만들어야 합니다.

> **왜 서울인가.** 건강 기록은 민감정보(개인정보보호법 제23조)입니다. 데이터가 한국에 있으면
> 설명할 것이 하나 줄고, 응답도 200ms쯤 빨라집니다.

만드는 데 2분쯤 걸립니다.

### ③ 표 만들기

왼쪽 메뉴 **SQL Editor** → **New query** → 이 저장소의 `server/schema.sql` 전체를 복사해서
붙여 넣고 → **Run**.

`Success. No rows returned` 나오면 된 겁니다.

### ④ 열쇠 두 개 복사

왼쪽 아래 **Settings**(톱니) → **API**.

| 이름 | 어디에 쓰나 | 알려주셔도 되나 |
|---|---|---|
| **Project URL** (`https://xxxx.supabase.co`) | 앱이 어디로 보낼지 | **네** |
| **anon / public key** | 앱이 로그인 전에 쓰는 열쇠 | **네** — 원래 앱 안에 들어가는 값입니다 |
| ~~service_role key~~ | 서버 전용 | **아니요. 절대 어디에도 붙여 넣지 마세요** |

`anon` 열쇠는 공개돼도 안전하게 **설계된** 값입니다. 남의 기록은 이 열쇠가 아니라 DB의 RLS
정책이 막습니다(`schema.sql`에 들어 있습니다). `service_role`은 그 정책을 **전부 무시하는**
열쇠라서 성격이 완전히 다릅니다.

### ⑤ 로그인 방식 켜기

왼쪽 메뉴 **Authentication** → **Providers**.

- **Email** — 기본으로 켜져 있습니다. 그대로 두세요.
- **Confirm email** 을 잠깐 꺼 두면 테스트가 편합니다 (Authentication → Sign In / Providers → Email).

**메일 발송이 진짜 벽입니다.** Supabase 기본 발송은 **시간당 두 통**이라, 회원 세 분이
한꺼번에 가입하면 세 번째 분은 메일을 못 받습니다. 아래 카카오·구글을 켜면 그 문제가
통째로 없어집니다 — **메일을 아예 안 보내기 때문입니다.**

### ⑥ 카카오·구글 로그인 (권장)

앱에는 이미 **`카카오로 시작하기` · `구글로 시작하기`** 버튼이 있습니다. Supabase와
각 콘솔에서 켜 주기만 하면 됩니다.

**먼저 Supabase에서 돌아올 주소를 등록합니다.**

```
Authentication → URL Configuration → Redirect URLs 에 추가
  https://byunsanggu.github.io/health_project/
```

이게 없으면 로그인하고 돌아오지 못합니다.

#### 카카오

지도 때문에 만드신 그 앱을 그대로 씁니다. 새로 만들 것 없습니다.

**1. 로그인 켜기**

```
developers.kakao.com → 볼륨 코치 → 제품 설정 → 카카오 로그인 → 활성화 ON
```

**2. 돌아올 주소와 Client Secret** — 둘 다 같은 화면에 있습니다.

```
앱 설정 → 플랫폼 키 → REST API 키 → [수정]
  · Redirect URI 에 추가:  https://<프로젝트-ref>.supabase.co/auth/v1/callback
  · Client Secret 발급 → 사용함(ON)
```

옛날 콘솔에서는 "카카오 로그인" 안에 Redirect URI가, "보안" 메뉴에 Client Secret이
따로 있었습니다. 지금은 **플랫폼 키 한 곳에 모여 있습니다.** 안 보인다고 헤매지 마세요.

**3. 동의항목 — 여기서 대부분 막힙니다.**

Supabase는 카카오에 **세 가지를 항상 요청합니다.** 앱이 고를 수 없습니다.

```go
// supabase/auth · internal/api/provider/kakao.go
oauthScopes := []string{"account_email", "profile_image", "profile_nickname"}
if scopes != "" { oauthScopes = append(oauthScopes, ...) }   // 덮어쓰기가 아니라 추가
```

authorize 주소에 `scopes=`를 붙여도 **빼지는 못하고 뒤에 더 붙기만 합니다.**
그래서 셋 다 카카오 쪽에서 열려 있어야 합니다.

```
제품 설정 → 카카오 로그인 → 동의항목
  · 닉네임        profile_nickname → 선택 동의
  · 프로필 사진    profile_image    → 선택 동의   ← "사용 안 함"이면 막힙니다
  · 카카오계정(이메일) account_email → 선택 동의
```

**세 번째가 문제입니다.** 개인 개발자 앱에서는 이메일이 "권한 없음"으로 잠겨 있고,
**비즈니스 앱으로 전환해야** 열립니다(카카오톡 채널 연결 + 사업자 정보. 전환 자체는
무료). 전환 전에는 무엇을 해도 KOE205가 납니다 — 앱 코드로 우회할 수 없습니다.

사업자등록이 없거나 지금 당장 열고 싶다면 두 가지 길이 있습니다.

- **구글만 먼저 켠다.** 구글은 이런 제약이 없어서 오늘 바로 됩니다.
- **카카오를 우리 서버로 직접 붙인다.** Supabase의 authorize 주소를 안 쓰고,
  Edge Function이 카카오와 토큰을 교환해 계정을 만들어 줍니다. 이러면 이메일을
  아예 요청하지 않아 비즈앱이 필요 없습니다. 대신 함수를 하나 더 만들고
  service_role 열쇠를 **Edge Function 비밀값에만** 넣어야 합니다(앱에는 절대 안 들어갑니다).

**4. Supabase에 넣기**

```
Authentication → Providers → Kakao → 켜기
  REST API Key      ← 앱 키의 REST API 키   (Client Secret 아님. 자주 바꿔 넣습니다)
  Client Secret     ← 2번에서 발급한 값
  Allow users without an email → 반드시 ON
```

마지막 줄이 중요합니다. 비즈앱이어도 이메일은 **선택 동의**라 사용자가 거부할 수
있고, 이게 꺼져 있으면 Supabase가 "이메일 없는 사용자"를 거부해서 동의까지 다 하고도
계정이 안 만들어집니다.

> **KOE205 (잘못된 요청)** — 설정되지 않은 동의항목을 요청했다는 뜻입니다.
> 3번의 세 항목을 순서대로 보세요. "사용 안 함"이나 "권한 없음"이 **하나라도**
> 남아 있으면 납니다.

**게시(In production)** 로 바꾸세요. 이메일·프로필 같은 기본 범위만 쓰면 구글 심사는
없고, 누르면 바로 바뀝니다.

카카오와 달리 구글은 이메일을 줍니다. 그래서 `scopes`를 따로 붙이지 않고 기본값을
그대로 씁니다.

### ⑦ 다시 부르기 (웹 푸시)

이번 주가 빡빡한 사람에게 한 번 알림을 보냅니다. **아프다고 적으신 분은 부르지 않습니다.**

**누가 판단하는가** — 앱입니다. 서버는 앱이 적어 둔 것을 시간 맞춰 보내기만 합니다.
서버가 판단하려면 그 사람의 통증·세션 기록을 읽어야 하는데, 그건 민감정보라
읽을 필요가 없는 곳에서 읽게 만들면 언젠가 샙니다. `push_queue` 표에는
**주소와 시각과 문장**밖에 없습니다.

**1. 열쇠 한 쌍 만들기** — 내 컴퓨터에서, 한 번만

```
npx web-push generate-vapid-keys
```

공개 열쇠(87자)와 비밀 열쇠(43자)가 나옵니다. 창을 닫지 마세요.

**2. 표 만들기**

```
Supabase → SQL Editor → New query
  server/schema.push.sql 전체 복사 → Run
```

**3. 열쇠 넣기 — 둘을 다른 곳에 넣습니다**

| 열쇠 | 어디에 | 왜 |
|---|---|---|
| **공개** 열쇠 | GitHub → Settings → Secrets → Actions → `VAPID_PUBLIC_KEY` | 브라우저가 구독할 때 그대로 씁니다. 공개해도 되는 값입니다 |
| **비밀** 열쇠 | Supabase → Edge Functions → Secrets → `VAPID_PRIVATE_KEY` | 새면 **아무나 이 앱 이름으로 남의 폰에 알림을 보낼 수 있습니다** |

비밀 열쇠를 `VAPID_PUBLIC_KEY`에 넣으면 빌드가 섭니다(길이가 다릅니다).

**4. 보내는 함수 올리기**

```
Supabase → Edge Functions → Deploy a new function
  이름: send-nudges
  파일: index.ts
  내용: server/functions/send-nudges/index.ts 전체
  Verify JWT: 켜 둡니다 (사람이 부르는 함수가 아닙니다)
```

비밀값 네 개를 넣습니다:

```
VAPID_PRIVATE_KEY   1)의 비밀 열쇠
VAPID_PUBLIC_KEY    1)의 공개 열쇠
VAPID_SUBJECT       mailto:관장님메일
SERVICE_ROLE_KEY    Settings → API → service_role
```

> **service_role은 여기 말고 어디에도 넣지 마세요.** 이 함수는 모든 사용자의
> 예약을 읽어야 해서 어쩔 수 없이 필요합니다. 앱 빌드에는 절대 들어가면 안 됩니다.

**5. 걸기**

```
Supabase → Integrations → Cron
  일정: 0,15,30,45 * * * *   (매 15분)
  하는 일: send-nudges 호출
```

**아이폰은 설치해야 옵니다.** iOS는 홈 화면에 설치한 PWA에만 푸시를 줍니다(16.4+).
사파리 탭에서는 권한 창조차 안 뜹니다 — 앱이 그 경우를 알아보고 "홈 화면에
설치하셔야 합니다"라고 적습니다.

**켜는 곳** — 앱의 오늘 탭 → 연속 카드 안의 "이번 주가 빡빡하면 불러 드릴까요?"

**언제 안 부르는가** (`src/engine/nudge.ts`)

| | |
|---|---|
| 통증 7점 이상 | 앱 스스로 "중단하세요"라고 하는 상태입니다. 부르면 한 입으로 두말입니다 |
| 이번 주 약속을 이미 지킴 | |
| 그날 이미 운동함 | |
| 이번 주에 이미 두 번 불렀음 | 그 이상은 광고입니다 |
| 마지막으로 부른 지 40시간 안 됨 | |

문구에 "사라집니다 · 실패 · 놓쳤습니다" 같은 말은 쓰지 않습니다. 테스트가 막습니다.

### ⑧ 친구 · 챌린지

친구와 **서로 이번 주에 몇 번 나왔는지만** 봅니다.

```
Supabase → SQL Editor → New query
  server/schema.friends.sql 전체 복사 → Run
```

**보이는 것 / 안 보이는 것**

| 보입니다 | 안 보입니다 |
|---|---|
| 별명 | 무게 · 종목 · 세트 |
| 이번 주 몇 번 / 목표 | 체중 · 통증 |
| 연속 몇 주 | 다니는 헬스장 · 운동 시각 |

건강 정보는 민감정보(제23조)라 친구에게 보이려면 완전히 다른 동의가
필요하고, 그 동의를 받는다 해도 남의 스쿼트 무게는 동기부여가 아니라
비교질이 됩니다.

**구조적으로 못 새게 해 뒀습니다.** 이 스키마는 `records` 표를 아예
쳐다보지 않습니다. 주간 요약(`week_summaries`)을 각자가 직접 올리고 친구는
그것만 봅니다 — 새고 싶어도 통로가 없습니다.

**친구 맺기는 코드로만**

이름이나 번호로 검색되게 만들면 모르는 사람이 붙습니다. 헬스장은 실제
장소라 "이 사람은 화·목 저녁에 온다"가 새면 위험합니다. 여섯 글자 코드를
직접 주고받은 사이만 친구가 됩니다. `0·O·1·I·L`은 안 씁니다 — 카톡으로
받아 적다 헷갈리면 그 사람은 다시 시도하지 않습니다.

승낙 단계는 없습니다. 코드를 건네준 것이 이미 승낙입니다. 대신 **끊기는
언제든, 상대에게 알림 없이** 됩니다.

**쪽지는 없습니다**

정해진 문구 네 개만 보낼 수 있고, 하루에 친구당 한 번입니다.

```
오늘 갑시다 👊 · 좋아요 👍 · 고생했어요 · 이번 주 같이 채웁시다
```

자유롭게 쓴 말을 담는 칸이 **표에 아예 없습니다.** 칸이 없으면 괴롭힘도
스팸도 유출도 통로가 없습니다.

**챌린지 — 목표는 각자 목표의 합**

```
나 주 4회 + 영수 주 3회  →  둘이 합쳐 이번 주 7번
```

앱이 "이번 주 10번!"을 정해 주면, 주 3회 하기로 한 사람이 친구 때문에
5번 나옵니다. **그건 챌린지가 아니라 부상입니다.** 각자 자기 약속만
지키면 챌린지도 저절로 채워집니다.

경쟁이 아니라 합산인 이유도 같습니다. 누가 더 했는지 줄 세우면 무리하는
사람이 나옵니다. 무게나 볼륨으로는 더더욱 줄 세우지 않습니다.

**확인한 것** (`server/schema.friends.test.sql`, 실제 PostgreSQL 16)

남의 프로필·요약은 안 보이고, 코드를 표에서 긁을 수 없고, 친구 출석은 못
고치고, 친구가 아닌 사람에게는 응원이 안 가고, 남인 척 보낼 수 없고,
정해지지 않은 문구는 DB가 막고, 끊으면 양쪽이 같이 끊깁니다.

### ⑨ 돌아왔을 때 (복귀)

서버 설정이 필요 없습니다. 기기 안에서 돕니다.

사람들이 운동 앱을 지우는 순간은 대개 여기입니다. 다치거나, 여행을 가거나,
일이 바빠서 몇 주 쉽니다. 그러고 다시 열면 앱이 **쉬기 전 무게를 그대로**
띄웁니다. 그걸 들다 실패하고, 실패하면 다음 주에 안 옵니다.

옆에 트레이너가 있으면 절대 안 생기는 일입니다. "얼마나 쉬셨어요?"를 묻고
무게를 내려 주니까요.

**한 주까지는 손대지 않습니다.** 쉬는 날은 프로그램 안에 이미 들어 있습니다.

**왜 쉬었는지 먼저 묻습니다.** 바빠서 쉰 2주와 다쳐서 쉰 2주는 전혀 다른
2주입니다 — 종목을 뺄 때 "왜요?"를 먼저 묻는 것과 같습니다.

| 공백 | 첫 주 무게 | 돌아오는 데 |
|---|---|---|
| ~1주 | 그대로 | — |
| 2주 | 95% | 1주 |
| 3~4주 | 90% | 2주 |
| 1~2달 | 80% | 3주 |
| 2~4달 | 70% | 4주 |
| 그 이상 | 65% | 4주 |

다쳐서 쉬었으면 여기서 10%p 더 내리고 한 주 더 쓰며, 앓고 났으면 5%p 더
내리고 세트를 더 줄입니다. 아무리 오래 쉬어도 **50% 아래로는 안 내립니다** —
그 아래는 운동이 아니라 사람을 무시하는 숫자입니다.

**겁주지 않습니다.** 돌아온 사람이 제일 두려워하는 것은 "다 날아갔겠지"이고,
그 생각이 들면 아예 안 옵니다. 실제로 근력은 생각보다 덜 빠지고, 한 번 키운
근육은 다시 붙는 것도 빠릅니다. 그 말을 먼저 합니다.

**세트를 중량보다 먼저 돌려줍니다.** 세트를 줄인 채 무게만 올리면 자극이
모자란 주가 길어집니다.

#### 붙이지 말 것 — 개인 Gmail을 SMTP로

Gmail을 발송 서버로 쓸 수는 있지만 권하지 않습니다. 하루 발송 한도가 낮고, 보내는
도메인이 안 맞아 스팸함으로 잘 가고, 갑자기 늘면 **개인 계정이 정지될 수 있습니다.**
같은 수고로 Resend 같은 곳을 붙이는 편이 안전합니다(월 몇천 통까지 무료).

### 로그인이 도는 방식

앱은 SDK 없이 주소만 씁니다.

```
[카카오로 시작하기]
  → {supabase}/auth/v1/authorize?provider=kakao&redirect_to={앱 주소}
  → 카카오 로그인
  → 앱 주소#access_token=... 로 돌아옴
  → 앱이 거두고 **주소창에서 즉시 지움**
```

주소에 토큰이 남아 있으면 그 주소를 복사해 공유하는 순간 로그인 정보가 같이 갑니다.
그래서 거두자마자 `history.replaceState`로 지웁니다.

떠나기 전에 **온보딩을 먼저 끝내 둡니다.** 페이지를 통째로 다른 주소로 보내는 것이라,
저장하지 않고 보내면 돌아왔을 때 설문을 처음부터 다시 하게 됩니다. 로그인하러 갔다가
설문을 다시 하게 되면 그때 앱을 지웁니다.

## 2-B. 헬스장 검색 붙이기 (`functions/gym-search`)

기록 동기화와 별개입니다. 이것만 따로 해도 되고, 안 해도 앱은 돕니다.

### 왜 서버를 거치는가

앱이 카카오를 직접 부르게 만들면 **앱을 받은 사람마다 카카오 개발자 계정을 만들어 열쇠를
넣어야 합니다.** 그러면 아무도 안 씁니다.

열쇠는 관장님 것 하나면 되고, 그건 서버에만 있으면 됩니다. 그러면 세 가지가 한꺼번에
해결됩니다.

- 사용자는 아무것도 안 넣고 바로 검색합니다
- 열쇠가 브라우저에 안 보이니 새어 나갈 것이 없습니다
- 서버끼리 부르는 것이라 브라우저가 막을 일도, 카카오에 도메인을 등록할 일도 없습니다

카카오 REST 열쇠는 Supabase `anon` 열쇠와 **성격이 다릅니다.** `anon`은 공개돼도 안전하게
설계된 값이지만, 카카오 열쇠는 가져간 사람이 관장님 하루 한도를 대신 써 버립니다.

### ① 카카오 열쇠 받기

[developers.kakao.com](https://developers.kakao.com) → 앱 만들기 →
**제품 설정 → 카카오맵 → 활성화** → 앱 키 → **REST API 키**.

카카오맵 활성화를 빼먹으면 열쇠는 멀쩡한데 장소 검색만 안 열립니다. 제일 많이 하는
실수입니다.

### ② 카카오 열쇠를 서버에 넣기

Supabase → **Edge Functions** → **Secrets**

| Key | Value |
|---|---|
| `KAKAO_REST_KEY` | 카카오 REST API 키 |

저장소에는 넣지 마세요. 이 열쇠는 서버에만 있으면 됩니다.

### ②-B 네이버도 붙이기 (선택)

**카카오맵 웹에는 있는데 카카오 로컬 API에는 없는 헬스장이 있습니다.** 두 쪽이 같은
색인을 안 씁니다. 실제로 "바우짐"이 그랬습니다 — 지도에서는 나오는데 API는 0개를
줬습니다.

그래서 네이버를 **대신이 아니라 뒤에** 둡니다. 카카오로 먼저 찾고 결과가 셋보다
적을 때만 네이버에 한 번 더 물어서 보탭니다. 안 넣어도 검색은 그대로 돌아갑니다.

| Key | Value |
|---|---|
| `NAVER_CLIENT_ID` | 네이버 개발자센터 애플리케이션의 Client ID |
| `NAVER_CLIENT_SECRET` | 같은 애플리케이션의 Client Secret |

**새 애플리케이션으로는 검색 API를 못 받습니다.** 네이버가 신규 등록을 닫아서,
새로 만들면 "신규로 등록할 수 없는 API가 선택되었습니다"가 뜹니다. **예전에 만든
애플리케이션은 권한을 그대로 들고 있으므로** 그 앱의 열쇠를 쓰세요. 애플리케이션
목록 → 연필 → `사용 API`에 **검색**이 있으면 그 앱입니다.

네이버 지역검색은 한 번에 **다섯 개**까지고 거리순 정렬도 거리 값도 없습니다.
그래서 보조로만 씁니다. 좌표는 줄 때도 있고 아닐 때도 있어서, 한반도 밖으로
떨어지는 값은 버립니다 — 그 줄은 거리만 안 보이고 고르는 데는 지장이 없습니다.

### ③ 함수 올리기 — 브라우저만으로

CLI를 안 깔아도 됩니다.

Supabase → **Edge Functions** → **Deploy a new function** → **Via Editor**

- 이름: `gym-search` (정확히 이 이름이어야 합니다 — 앱이 이 이름으로 부릅니다)
- **Verify JWT: 끄기** ← 이걸 켜 두면 로그인한 사람만 검색됩니다
- 내용: 이 저장소의 `server/functions/gym-search/index.ts` 전체를 붙여넣기

**Verify JWT를 끄는 이유가 두 가지입니다.**

하나는 처음 켠 사람이 제일 먼저 하는 일이 헬스장 고르기인데, 그 앞에 회원가입을
세워 두면 거기서 절반이 나갑니다.

둘은 더 실질적입니다 — 새 형식 열쇠(`sb_publishable_...`)는 JWT가 아니라서,
켜 두면 **로그인한 사람도 못 지나갑니다.** 게이트웨이가 열쇠를 검사하는 건
그대로이므로 아무나 부를 수 있게 되는 것은 아닙니다.

### CLI로 하시려면

```sh
npm install -g supabase
supabase login
supabase link --project-ref <프로젝트-ref>       # 대시보드 주소에 있는 그 값
supabase secrets set KAKAO_REST_KEY=<REST API 키>
supabase functions deploy gym-search --no-verify-jwt
```

`--no-verify-jwt`를 쓰는 이유: **로그인 안 한 사람도 헬스장은 찾을 수 있어야 합니다.** 처음
켠 사람이 제일 먼저 하는 일이 헬스장 고르기인데, 그 앞에 회원가입을 세워 두면 거기서 절반이
나갑니다. 대신 Supabase 게이트웨이가 이 프로젝트의 열쇠를 가진 요청만 함수까지
들여보냅니다.

### ④ 됐는지 보기

앱 → **헬스장** 탭 → 검색창에 `경기도`.

| 칸 오른쪽 위 | 뜻 |
|---|---|
| **전국 검색** | 서버를 지나갑니다 — 이게 맞는 상태입니다 |
| **전국 검색 · 이 기기** | 아직 기기에 넣은 열쇠로 부르고 있습니다 |
| **직접 등록** | 검색이 아예 안 켜져 있습니다 |

안 되면 앱이 이유를 말해 줍니다. 사용자는 열쇠를 넣은 적이 없으므로 "열쇠가
틀렸습니다" 같은 말은 절대 안 나옵니다 — 고칠 수도 없는 일로 사용자를 보내는
셈이기 때문입니다. 대신 뒤에서 무슨 일인지는 이렇게 갈립니다.

| 앱에 뜨는 말 | 실제로는 | 고칠 곳 |
|---|---|---|
| 검색이 아직 준비되지 않았습니다 | 404 — 함수를 아직 안 올림 | ③ |
| 〃 | 401 — Verify JWT가 켜져 있음 | ③ |
| 〃 | 503 — 카카오 열쇠를 서버에 안 넣음 | ② |
| 오늘 검색 한도를 다 썼습니다 | 429 — 카카오 하루 한도 | 내일 |
| 연결이 안 됩니다 | 인터넷이 없음 | — |

로그는 여기서 봅니다:

```sh
supabase functions logs gym-search
```

대시보드에서는 Edge Functions → `gym-search` → **Logs**.

### 열쇠를 바꿀 때

```sh
supabase secrets set KAKAO_REST_KEY=<새 키>
```

다시 배포할 필요 없습니다. 카카오 콘솔에서 옛날 열쇠를 지우면 끝입니다.

### 앱 안의 "이 기기에서만 켜기"는 뭔가

헬스장 탭에 **`검색을 이 기기에서만 켜기 (만든 사람용)`** 이 있습니다. 서버를 붙이기 전에
혼자 시험해 보는 길입니다. 사용자에게 보여줄 기능이 아니고, 서버가 붙으면 앱이 알아서 서버
쪽을 씁니다 — 기기에 열쇠가 남아 있어도 서버가 먼저입니다.

## 2-C. 헬스장 정보 공유 (`schema.gyms.sql`)

기구 목록을 여러 사람이 같이 채웁니다. 카카오가 주는 건 이름과 주소뿐이고,
**"여기 핵스쿼트 있나"는 실제로 다니는 사람만 압니다.**

SQL Editor → New query → `server/schema.gyms.sql` 전체 → Run.
(`schema.sql`을 먼저 돌린 뒤에 합니다. 두 번 돌려도 안전합니다.)

### 나누는 것과 안 나누는 것

| | 예 |
|---|---|
| 나눔 | 헬스장 이름·주소·층, 어떤 기구가 있고 없는지 |
| **안 나눔** | 내 기록, 통증, 체중, 어떤 종목을 왜 뺐는지(아파서) |

### 누가 갈 수 있는 곳인가

선은 "상업 헬스장이냐"가 아니라 **"남의 집이냐"** 입니다.

| | 검색 | 왜 |
|---|---|---|
| `public` 상업 헬스장 | 나옴 | 누구나 갈 수 있다 |
| `restricted` 아파트·회사·호텔 | 나옴 · "입주민·직원 전용" 딱지 · 뒤로 밀림 | 밖에서는 뭐가 있는지 알 길이 없어서, 같은 단지 사람이 채워 준 목록이 제일 값어치가 크다 |
| `private` 홈짐 | **안 나옴** | 남의 집 주소다 |

아파트 헬스장을 홈짐과 같이 묶었던 것이 처음 설계였는데, 그건 잘못 그은
선이었습니다. 같은 단지 주민 둘이 각자 등록하면 기구 목록이 두 벌로 쪼개지고,
크라우드소싱이 제일 필요한 곳에서 안 되는 셈이 됩니다.

`private`는 DB가 막습니다 — check 제약과 함수 양쪽에서.

아파서 뺀 종목은 서버에 올라가지 않습니다. 익명으로 모아도 "이 헬스장
사람들이 허리가 아프다"는 말이 만들어지는데, 그건 우리가 만들어도 되는
말이 아닙니다(민감정보). **앱이 안 보내고, DB가 한 번 더 막습니다.**

### 믿을 수 있게 만드는 장치

기구 목록을 헬스장 행에 배열로 넣으면 나중에 쓴 사람이 앞사람 것을 통째로
덮어씁니다. 그래서 **사람마다 기구마다 한 줄**을 남깁니다.

- `3명이 확인 · 마지막 2주 전` 을 보여줄 수 있습니다
- 장난으로 하나 찍은 사람이 전체를 뒤집지 못합니다
- **있음과 없음이 같으면 없는 쪽으로 봅니다** — 없는데 있다고 하면 헬스장에
  가서 못 하고, 있는데 없다고 하면 종목 하나가 덜 나올 뿐입니다

### 확인한 것

로컬 PostgreSQL 16에서 RLS를 우회하지 않는 역할로 실제로 돌렸습니다.

```
[가] 헬스장 올리기 → 기구 3개
[나] 같은 헬스장에 기구 2개
[확인] 이름이 안 바뀌었나 → 바우짐          ← 나중 사람이 못 덮어씀
[기구] barbell-set · 2명 확인
[기구] 핵스쿼트가 목록에 없나 → 없음 ✓       ← 있음1 없음1이면 없는 쪽
[RLS] 남의 확인 기록 고치기 → 0줄 바뀜
[RLS] 남의 id로 확인 남기기 → 막힘 ✓
[민감정보] 통증이 안 들어갔나 → 안 들어감 ✓
[민감정보] 직접 INSERT로 통증 넣기 → 막힘 ✓  ← check 제약
[단지] 아파트 헬스장 올리기 → 1개            ← 같은 단지 주민끼리 나눈다
[단지] 딱지가 남았나 → restricted
[사생활] 홈짐 올리기 → 0개                  ← 남의 집 주소는 안 올라감
[탈퇴] 가의 확인 기록 → 0줄 / 나의 것 → 2줄
[탈퇴] 헬스장 자체 → 남음 ✓
```

다시 돌려 보려면 `schema.test.sql`과 같은 방법으로:

```bash
psql -h /tmp -p 5433 -U app_user -d postgres -f server/schema.gyms.test.sql
```

### 뷰에 security_invoker를 켜는 이유

Supabase가 `gym_equipment_summary`에 **UNRESTRICTED · Security Definer view**
라고 빨간 딱지를 붙이면 맞는 지적입니다.

PostgreSQL의 뷰는 기본이 "만든 사람 권한으로 도는 것"입니다. 이 뷰는
`postgres`가 만들고 `postgres`는 RLS를 우회하므로, 그대로 두면 **뷰가 밑에
깔린 표의 RLS를 건너뜁니다.**

지금은 `gym_equipment`의 읽기 정책이 `using (true)`라 실제로 새는 것은
없습니다. 다만 나중에 읽기를 좁히는 순간 **이 뷰만 조용히 옛날처럼 다
보여주게 됩니다.** 그때는 좁힌 줄 알고 있으니 아무도 안 봅니다.

```sql
create or replace view public.gym_equipment_summary
with (security_invoker = true) as ...
```

이미 돌리신 뒤에 이 줄이 없다면, 이것만 따로 돌리면 됩니다:

```sql
alter view public.gym_equipment_summary set (security_invoker = true);
```

### 탈퇴

`delete_my_data()`(기록·설정)와 `delete_my_gym_data()`(기구 확인·뺀 종목)를
둘 다 불러야 합니다. 헬스장 자체는 남습니다 — 다른 사람들이 쓰고 있고, 거기엔
내 정보가 없습니다.

## 스키마는 확인하고 드립니다

붙여넣고 나서 "안 되는데요"를 주고받는 것보다, 먼저 틀려 보는 편이 쌉니다. `schema.sql`은 로컬
PostgreSQL 16(Supabase와 같은 버전)에서 실제로 돌려 확인했습니다.

```
[가] 올리기 → 1줄
[가] 내 기록 보임 → 1줄
[나] 가의 기록 보임 → 0줄              ← RLS가 막습니다
[나] 남의 id로 INSERT → 막힘 ✓         ← with check가 막습니다
[가] 오래된 것 올리기 → 0줄 바뀜        ← 새 기록을 안 덮습니다
[가] synced_at이 updated_at보다 뒤 → ✓  ← 서버가 적습니다
[가] 설정 user_id 자동 → ✓
[가] 탈퇴 후 남은 기록 → 0줄
```

다시 돌려 보려면:

```bash
initdb -D /tmp/pgcheck -A trust -U postgres
pg_ctl -D /tmp/pgcheck -o "-k /tmp -p 5433" start
psql -h /tmp -p 5433 -U postgres -f server/schema.stub.sql   # auth.uid() 흉내
psql -h /tmp -p 5433 -U postgres -f server/schema.sql
psql -h /tmp -p 5433 -U postgres -f server/schema.roles.sql  # RLS 우회 안 하는 역할
psql -h /tmp -p 5433 -U app_user -d postgres -f server/schema.test.sql
```

`postgres` 역할은 **BYPASSRLS**라서 그대로 시험하면 정책이 늘 통과합니다 — 그러면 아무것도
확인하지 못한 것입니다. 그래서 따로 역할을 만들어 씁니다.

## 설계에서 신경 쓴 것

### 시계가 다른 폰 때문에 기록을 잃지 않기

기록마다 시각이 둘입니다.

- `updated_at` — **기기가** 적습니다. 충돌은 이 값으로 풉니다(나중에 고친 쪽이 이깁니다).
- `synced_at` — **서버가** 적습니다. "지난번 이후 바뀐 것"은 반드시 이 값으로 고릅니다.

둘을 합치면 안 됩니다. 시계가 5분 느린 폰이 올린 기록은, 기기 시각으로 거르면 다음 동기화에서
걸러져 **영영 안 내려옵니다.** 기록을 잃는 버그이고, 잃고 나서야 알게 됩니다.

### 오래된 기록이 새 기록을 덮지 않기

비행기 모드였던 폰이 사흘 뒤에 연결됐다고 그 사흘치가 사라지면 안 됩니다. `push_records`가
**서버에 있는 것보다 새 것일 때만** 덮어씁니다. 앱에서 막지 않고 DB에서 막는 이유는, 앱은
여러 버전이 동시에 돌아다니지만 DB는 하나이기 때문입니다.

### 끊어서 올리기

한 달 치가 밀려 있으면 수백 개가 됩니다. 한 번에 다 보내면 지하철에서 끊기는 순간 전부
실패하고 처음부터 다시 합니다. 50개씩 끊어 보내고, **보낸 만큼은 아웃박스에서 뺍니다.**

### 남의 기록은 DB가 막기

RLS 한 줄이 전부입니다 — `auth.uid() = user_id`. 앱 코드에 버그가 나도 남의 기록이 새지
않습니다. 건강 정보를 다루는 이상 "앱이 잘 짜여 있으니 괜찮다"로는 부족합니다.

`with check`까지 걸어야 "남의 user_id로 INSERT"가 막힙니다. `using`만 걸면 읽기는 막히는데
쓰기가 뚫립니다.

### 지우는 길

`delete_my_data()`로 기록과 설정을 지우고, 계정을 지우면 남은 것도 `on delete cascade`로
같이 사라집니다. 지우는 길이 없으면 개인정보를 받을 자격이 없습니다.
