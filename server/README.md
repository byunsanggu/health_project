# 서버 붙이기

앱은 이미 **서버 없이 완전히 돌아갑니다.** 서버는 "같은 사람의 다른 기기"를 잇는 역할만 합니다 —
폰을 바꿔도 기록이 남고, 나중에 트레이너 모드가 붙습니다.

그래서 서버가 죽어도 앱은 멈추지 않습니다. 로컬에 먼저 쓰고, 보낼 것을 아웃박스에 쌓아
두었다가 연결되면 흘려보냅니다.

## 1. 관장님이 하실 것 (15분)

https://supabase.com → **Start your project** → GitHub 또는 이메일로 가입. 카드 필요 없습니다.

### ② 프로젝트 만들기 — **리전을 꼭 Seoul로**

**New project** 누르고,

| 칸 | 넣을 값 |
|---|---|
| Name | `volume-coach` |
| Database Password | **길게 아무거나. 어딘가에 적어 두세요** — 다시 못 봅니다 |
| Region | **Northeast Asia (Seoul)** ← 이게 제일 중요합니다 |
| Plan | Free |

리전을 잘못 고르면 나중에 못 바꿉니다. 프로젝트를 새로 만들어야 합니다.

> **왜 서울인가.** 건강 기록은 민감정보(개인정보보호법 제23조)입니다. 데이터가 한국에 있으면
> 설명할 것이 하나 줄고, 응답도 200ms쯤 빨라집니다.

만드는 데 2분쯤 걸립니다.

### ③ 표 만들기

왼쪽 메뉴 **SQL Editor** → **New query** → 이 저장소의 `server/schema.sql` 전체를 복사해서
붙여 넣고 → **Run**.

`Success. No rows returned` 나오면 된 겁니다.

### ④ 열쇠 두 개 복사

왼쪽 아래 **Settings**(톱니) → **API**.

| 이름 | 어디에 쓰나 | 알려주셔도 되나 |
|---|---|---|
| **Project URL** (`https://xxxx.supabase.co`) | 앱이 어디로 보낼지 | **네** |
| **anon / public key** | 앱이 로그인 전에 쓰는 열쇠 | **네** — 원래 앱 안에 들어가는 값입니다 |
| ~~service_role key~~ | 서버 전용 | **아니요. 절대 어디에도 붙여 넣지 마세요** |

`anon` 열쇠는 공개돼도 안전하게 **설계된** 값입니다. 남의 기록은 이 열쇠가 아니라 DB의 RLS
정책이 막습니다(`schema.sql`에 들어 있습니다). `service_role`은 그 정책을 **전부 무시하는**
열쇠라서 성격이 완전히 다릅니다.

### ⑤ 로그인 방식 켜기

왼쪽 메뉴 **Authentication** → **Providers**.

- **Email** — 기본으로 켜져 있습니다. 그대로 두세요.
- **Confirm email** 을 잠깐 꺼 두면 테스트가 편합니다 (Authentication → Sign In / Providers → Email).
  실제로 쓰기 전에 다시 켜세요.

카카오 로그인은 나중에 붙일 수 있습니다. 카카오 개발자 등록이 따로 필요해서(15분쯤) 우선
이메일로 돌려 보고, 쓸 만하면 그때 하시는 게 낫습니다.

## 3. 제가 만들어 둔 것

| 파일 | 하는 일 |
|---|---|
| `server/schema.sql` | 표 두 개 + RLS 정책 + 올리기 함수 + 탈퇴 함수 |
| `src/engine/sync.ts` | 올리고 받고 합치는 규칙 (서버가 뭔지 모릅니다) |
| `src/engine/storage.ts` | 오프라인 저장과 아웃박스 (전부터 있었습니다) |

열쇠를 받으면 만들 것: 로그인 화면, 실제 전송(`fetch`), 설정 탭의 동기화 상태 줄, 탈퇴 버튼.

## 설계에서 신경 쓴 것

### 시계가 다른 폰 때문에 기록을 잃지 않기

기록마다 시각이 둘입니다.

- `updated_at` — **기기가** 적습니다. 충돌은 이 값으로 풉니다(나중에 고친 쪽이 이깁니다).
- `synced_at` — **서버가** 적습니다. "지난번 이후 바뀐 것"은 반드시 이 값으로 고릅니다.

둘을 합치면 안 됩니다. 시계가 5분 느린 폰이 올린 기록은, 기기 시각으로 거르면 다음 동기화에서
걸러져 **영영 안 내려옵니다.** 기록을 잃는 버그이고, 잃고 나서야 알게 됩니다.

### 오래된 기록이 새 기록을 덮지 않기

비행기 모드였던 폰이 사흘 뒤에 연결됐다고 그 사흘치가 사라지면 안 됩니다. `push_records`가
**서버에 있는 것보다 새 것일 때만** 덮어씁니다. 앱에서 막지 않고 DB에서 막는 이유는, 앱은
여러 버전이 동시에 돌아다니지만 DB는 하나이기 때문입니다.

### 끊어서 올리기

한 달 치가 밀려 있으면 수백 개가 됩니다. 한 번에 다 보내면 지하철에서 끊기는 순간 전부
실패하고 처음부터 다시 합니다. 50개씩 끊어 보내고, **보낸 만큼은 아웃박스에서 뺍니다.**

### 남의 기록은 DB가 막기

RLS 한 줄이 전부입니다 — `auth.uid() = user_id`. 앱 코드에 버그가 나도 남의 기록이 새지
않습니다. 건강 정보를 다루는 이상 "앱이 잘 짜여 있으니 괜찮다"로는 부족합니다.

`with check`까지 걸어야 "남의 user_id로 INSERT"가 막힙니다. `using`만 걸면 읽기는 막히는데
쓰기가 뚫립니다.

### 지우는 길

`delete_my_data()`로 기록과 설정을 지우고, 계정을 지우면 남은 것도 `on delete cascade`로
같이 사라집니다. 지우는 길이 없으면 개인정보를 받을 자격이 없습니다.

## 남은 법적 숙제

서버를 붙이면 **개인정보 처리방침에 두 줄이 더 필요합니다.**

1. **위탁** — "Supabase Inc.(미국)에 데이터 보관을 위탁하며, 보관 위치는 대한민국(서울)입니다"
2. **국외이전** — 서울 리전이어도 운영사가 해외라 국외에서 접근 가능한 구조입니다.
   고지·동의가 필요한지는 **확인이 필요합니다.**

제가 단정할 영역이 아닙니다. 개인정보보호위원회 상담 **1833-6972**가 무료입니다.
문구는 확인하신 내용에 맞춰 제가 쓰겠습니다.

이게 걸리면 **Oracle Cloud 서울 리전 무료 VM**이 대안입니다. 관장님 명의 서버라 국외이전
자체가 없습니다. 대신 서버 관리를 계속 하셔야 합니다.
