# 적응형 볼륨 주기화 트레이닝 엔진

주간 볼륨과 피로도를 읽고 **다음 주 훈련량을 스스로 조절하는** 트레이닝 엔진입니다.

대부분의 운동 앱은 "오늘 뭐 할지"를 정해줍니다. 이 엔진은 그다음 질문을 풉니다 —
**이번 주 볼륨이 회복 가능한 범위인가, 지금 몸이 이 루틴을 받아낼 상태인가.**

## 왜 이걸 만드나

현장에서 회원이 정체되는 지점은 종목 선택이 아니라 총량 관리입니다.

| 기존 앱이 하는 것 | 이 엔진이 추가로 하는 것 |
|---|---|
| 오늘의 루틴 추천 | 부위별 **주간 유효 세트** 집계와 MEV/MAV/MRV 구간 판정 |
| kg × reps 기록 | **RIR(남은 반복 수)** 기반 수행 품질 측정 |
| 세션 단위 진행 | 4~6주 **메조사이클**과 자동 **디로드** 삽입 |
| 주간 총량만 계산 | **훈련 빈도** — 같은 볼륨도 한 세션에 몰면 덜 인정한다 |
| 고정 루틴 | **통증 체크인**에 따른 종목 자동 대체 |
| 고정 증량 단위 | **등록한 헬스장 기구**가 만들 수 있는 중량으로만 처방 |
| "알아서 넣으세요" | 첫 종목의 **시작 중량 추정**과 탐색 세트 보정 |
| 자가 신고 경력 | **경력 4단계**를 훈련 기간·기록과 대조해 과대 신고를 낮춰 잡음 |
| 고정 루틴 목록 | 경력·일수·보유 기구로 **첫 프로그램 자동 생성** |
| RIR 신고를 그대로 신뢰 | **실패 세트와 대조해 신고 편향을 역산**하고 집계·처방에 반영 |
| 온라인 전제 | **오프라인 우선** 저장 — 헬스장 지하에서도 기록이 남는다 |
| 헬스장 한 곳 | **여러 곳 등록·전환** — 기구가 다르면 종목이 자동으로 대체된다 |
| 한 가지 루틴 | **블록 유형 5종** — 근비대 · 근력 · 고밀도 · 한계 돌파 · 컨디셔닝 |
| 고정 세트 수 | **수행을 보고 세트를 조절** — 잘 나오면 늘리고 무너지면 멈춘다 |
| 시간 제약 무시 | **쓸 수 있는 시간에 맞춰** 세션을 줄인다 (고립부터, 메인은 지킴) |

## 빠르게 확인하기

```bash
npm install     # typescript, @types/node (런타임 의존성은 없습니다)
npm test        # 516개 테스트
npm run check   # 타입체크 + 테스트

node src/demo.ts   # 6주 블록 시뮬레이션
```

`demo.ts`는 가상의 중급자(78kg·중급)를 주 4회 6주간 훈련시키며 엔진이 한 바퀴 도는 것을 보여줍니다.
3주차에 어깨 통증이 생기면 종목이 대체되고, 4주차에 피로 신호가 임계를 넘으면 디로드가 삽입되고,
5주차에 새 축적 블록이 시작됩니다.

```
3주차 · 축적 3주차 · 목표 RIR 2 · 피로 점수 3
  ⚠ 평균 RIR이 3.0 → 2.0로 떨어졌습니다. 같은 중량이 더 무겁게 느껴지는 상태입니다 (+2)
  ⚠ 어깨 통증 4점. 바벨 벤치프레스 대신 머신 체스트프레스를 권합니다.

4주차 · 디로드 · 목표 RIR 4 · 피로 점수 9
  ⚠ 13개 종목의 추정 1RM이 지난주보다 떨어졌습니다 (랫 풀다운, 바벨 컬, 백 스쿼트 외) (+3)
  ⚠ 최근 7일 중 4일에 3점 이상 관절 통증이 보고됐습니다 (+3)

5주차 · 축적 1주차 · 목표 RIR 3 · 피로 점수 3
```

## 핵심 규칙

### 유효 세트 (`volume.ts`)

kg × reps만 세면 볼륨 관리가 무의미해집니다. 20회 남기고 끝낸 세트와 실패 직전까지 간 세트는 같은 1세트가 아닙니다.

| 조건 | 가중치 |
|---|---|
| 워밍업 | 0 |
| RIR 0~3 | 1.0 |
| RIR 4 | 0.7 |
| RIR 5+ | 0.3 |
| 5회 미만 | × 0.8 (근력 자극이 주) |
| 30회 초과 | × 0.6 |

여기에 종목별 부위 기여도(주동근 1.0, 협응근 0.5)를 곱해 합산합니다.
벤치프레스 4세트 = 가슴 4세트 + 삼두 2세트 + 전면삼각근 2세트.

### 훈련 빈도 (`frequency.ts`)

세션 경계를 무시하고 전부 더하면 안 됩니다. **한 세션에서 한 부위가 온전히 인정받는 상한은 9세트**이고, 넘은 만큼은 절반만 셉니다.

```
가슴 16세트를 하루에  → 유효 11.5세트 (4.5세트가 버려짐)
가슴 16세트를 이틀에  → 유효 16세트
```

권장 빈도는 볼륨에서 역산합니다 — 4세트 미만은 주 1회, 그 위는 최소 주 2회, 세션당 상한을 넘기면 `ceil(볼륨 ÷ 9)`회.

**볼륨보다 분배가 먼저입니다.** 한 세션에 몰린 부위에는 세트를 더 넣지 않고 "주 N회로 나누세요"를 먼저 처방합니다. 버려지는 세트를 늘리는 건 피로만 늘리니까요. 단 MEV 미만이면 늘리는 게 먼저고, MRV 초과면 줄이는 게 먼저입니다.

### 볼륨 진행 (`mesocycle.ts`)

| 현재 구간 | 처방 |
|---|---|
| MEV 미만 | MEV까지 끌어올림 |
| MEV ~ MAV | 주 +2세트 (피로 신호 있으면 +1) |
| MAV ~ MRV | 주 +1세트 (피로 신호 있으면 유지) |
| MRV 초과 | MRV로 되돌림 |
| 통증 보고 부위 | 유지 |
| 최근 4주 기록 없음 | 처방하지 않고 `neglected`로 따로 알림 |

### 중량 진행 (`load.ts`)

이중 진행 + RIR 보정. **순서가 중요합니다** — 반복 상단에 닿았어도 RIR이 목표보다 모자라면 올리지 않습니다.

| 마지막 본세트 | 처방 |
|---|---|
| 반복 상단 도달 + RIR 여유 | 증량 (여유 2 이상이면 두 칸) |
| 반복 상단 도달 + RIR 부족 | 유지 — RIR부터 확보 |
| 반복 미달 + RIR 여유 2 이상 | 증량 |
| 목표 하단 미달 | 10% 감량 |
| 범위 안 | 유지, 반복 +1 |

### 디로드 판정 (`readiness.ts`)

단일 신호로 결정하지 않습니다. 합산 점수 5점 이상에서 디로드를 권합니다.

| 신호 | 가중치 |
|---|---|
| 주요 종목 추정 1RM 하락 (2종목 이상) | 3 |
| 관절 통증 3점 이상이 주 2일 이상 | 3 |
| MRV 초과 부위 | 1~2 (3부위 이상이면 단독 트리거) |
| 평균 RIR 1 이상 하락 | 2 |
| 평균 수면 6시간 미만 또는 근육통 7점 이상 | 2 |
| 계획된 축적 주차 완료 | 2 |
| 의욕 3점 이하 | 1 |

디로드 주는 **볼륨 절반, 중량 90%, 목표 RIR 4**. 피로의 주된 원인은 볼륨이고, 강도를 유지해야 복귀 시 수행력이 살아 있습니다.

디로드 다음 주는 무조건 훈련으로 복귀하고, 디로드 주의 낮은 기록은 수행력 하락으로 세지 않습니다.
(이 두 규칙이 없으면 디로드가 디로드를 부르는 무한 루프에 빠집니다 — 시뮬레이션으로 잡은 버그입니다.)

### 헬스장 기구 (`gym.ts`)

종목마다 고정된 증량 단위를 쓰는 건 틀렸습니다. **그 헬스장의 기구가 가능한 중량을 결정합니다.**

| 기구 | 무엇이 다른가 |
|---|---|
| 바벨 | 빈 바가 20kg가 아닐 수 있음 (여성용 15, EZ바 10, 스미스머신은 제각각) |
| 플레이트 | 1.25kg 한 쌍이 없으면 2.5kg 단위로 못 올림 |
| 스택 머신 | 5kg 간격이 흔하지만 기구마다 다르고, 보조추가 있기도 함 |
| 플레이트식 머신 | 빈 캐리지가 이미 20~30kg |
| 덤벨 | 보유한 것만 쓸 수 있음 (23kg 덤벨은 없음) |

```
처방 82.5kg → 벤치프레스   82.5kg  (20kg 바 + 한쪽 25 · 5 · 1.25)
처방   37kg → EZ바 컬      37.5kg  (10kg 바 + 한쪽 10 · 2.5 · 1.25)
처방  160kg → 레그프레스    160kg   (20kg 캐리지 + 한쪽 25 · 25 · 20)  한 칸 = 10kg
처방   23kg → 덤벨          22kg   (보유 덤벨)
```

증량 중이면 위로, 감량·통증·디로드 중이면 아래로 붙여 **반올림이 처방의 의도를 되돌리지 않게** 합니다.

기구 보유 여부도 여기서 관리합니다. 종목 단위(`'hack-squat': 'unavailable'`)나 기구 종류 단위(`missingEquipment: ['smith']`)로 끄면, 세션 생성 시 자동으로 대체 종목이 들어가고 대체 후보에서도 빠집니다.

### 시작 중량 (`strength.ts`)

"내가 몇 kg을 들 수 있는지 모른다"에 대한 3단계 답입니다.

| 순서 | 방법 | 신뢰도 |
|---|---|---|
| 1 | **탐색 세트** — 가벼운 무게로 한 세트, RIR만 입력 → 추정 1RM 역산 | 높음 |
| 2 | **종목 간 환산** — 이미 하는 종목의 추정 1RM에서 계수로 변환 | 중간 |
| 3 | **체중 × 경력 기준선** — 5개 앵커 종목의 체중 배수 | 낮음 |

이미 하는 종목이 있으면 2번, 없으면 3번으로 제안하고, **어느 경로든 `needsCalibration`을 붙여** 첫 세트에서 확인하게 합니다. 제안값에는 안전 마진 10%를 빼고 기구 눈금에서 아래쪽으로 붙입니다 — 가벼우면 세트 중에 올리면 되지만 무거우면 다치니까요.

```
체중 75kg · 초급 남성, 기록 없음   → 벤치프레스 32.5kg 제안
벤치 80kg × 8회 (RIR 2) 기록 있음  → 인클라인 덤벨프레스 20kg (한쪽) 제안
탐색 세트 40kg × 10회 (RIR 4)      → 추정 1RM 58.5kg → 작업 중량 40kg 확정
```

환산 계수는 개인차와 기구 편차가 커서 정밀한 값이 아닙니다. "완전히 모름"을 "대충 이 근처"로 옮기는 용도이고, 탐색 세트 한 번이면 실측으로 대체됩니다.

### 경력 단계 (`levels.ts`)

네 단계가 볼륨 랜드마크만 바꾸는 게 아닙니다.

| 단계 | 기준 | 축적 주차 | 1주차 목표 RIR | 세션당 상한 |
|---|---|---|---|---|
| 초보 | 6개월 미만 | 6주 | 4 | 7세트 |
| 중급 | 6개월~2년 | 5주 | 3 | 9세트 |
| 고급 | 2~5년 | 4주 | 2 | 10세트 |
| 전문가 | 5년 이상 | 4주 | 2 | 11세트 |

전문가는 MEV가 가장 높지만 MRV는 그만큼 오르지 않습니다 — 쓸 수 있는 폭이 오히려 좁습니다.

**자가 신고는 그대로 믿지 않습니다.** 현장에서 "중급이요"라고 답하는 사람의 상당수가 6개월 미만입니다. 훈련 개월 수와 (있다면) 기록으로 대조해 **낮은 쪽**을 택합니다. 과대평가된 단계로 볼륨을 처방하면 몇 주 버티다 부상으로 끝나지만, 낮게 잡으면 몇 주 손해로 끝나기 때문입니다.

```
자가 신고 '고급' + 훈련 4개월 → 초보 볼륨으로 시작
자가 신고 '초보' + 훈련 60개월 → 초보 그대로 (올려 잡지 않음)
```

### 기구 카탈로그 (`equipment.ts`)

종목 41개를 하나씩 고르게 하면 아무도 온보딩을 끝내지 못합니다. **기구 단위**로 켜면 종목이 열립니다.

```
바벨 + 랙 + 벤치만            → 9종목
  + 케이블 스테이션            → +6종목 (푸시다운, 페이스 풀, 케이블 플라이 …)
  + 덤벨 세트                → +5종목
기본 구성(19개 기구)          → 73/83종목
```

벤치프레스는 바벨만으로는 안 되고 벤치가 있어야 합니다 — 종목마다 **필요 기구 전부**를 갖춰야 열립니다. 부위별 커버리지도 점검해서 "삼두 종목이 없습니다 → 케이블 스테이션을 추가하세요"까지 알려줍니다.

### 첫 프로그램 생성 (`onboarding.ts`)

설문 하나로 단계 판정 → 분할 선택 → 종목 배치 → 첫 주 처방까지 만듭니다.

| 주당 일수 | 분할 | 부위당 빈도 |
|---|---|---|
| 2일 | 전신 A/B | 2회 |
| 3일 | 전신 A/B/C | 2~3회 |
| 4일 | 상하체 분할 | 2회 |
| 5일 | 혼합 분할 | 2~3회 |
| 6일 | 푸시·풀·레그 2순환 | 2회 |

**주 3일에 PPL을 넣지 않았습니다.** 부위당 주 1회가 되어 빈도 모듈이 말하는 바와 모순되기 때문입니다 — 생성기가 자기 규칙을 어기면 앞뒤가 안 맞습니다.

종목 선택 규칙:
- 메인 자리에는 **프리웨이트 복합 동작**을 우선합니다. 머신으로만 채운 프로그램은 안전해 보이지만 배우는 게 없습니다.
- 초보자는 같은 값이면 관절 부담이 적은 쪽을 고르되, 기본 동작을 밀어낼 만큼은 아닙니다.
- **한 세션에 같은 관절을 거듭 싣지 않습니다.** 이 규칙이 없으면 스쿼트 → RDL → 데드리프트가 한 날에 몰립니다.
- 한 종목은 최대 4세트. 모자란 볼륨은 주간 처방이 몇 주에 걸쳐 올립니다.

### 여러 헬스장 (`gyms.ts`)

한 곳만 다니는 사람은 거의 없습니다. 집 근처와 회사 근처가 다르고, 출장지에서는 처음 가는 곳에서 해야 합니다. 그래서 헬스장은 하나의 설정값이 아니라 **목록**입니다.

- 여러 곳을 등록해 두고 그날 가는 곳으로 전환
- 전환하면 없는 기구가 필요한 종목이 **자동으로 대체**됩니다 (컨벤셔널 데드리프트 → 케이블 풀스루)
- **찾기** — 이름·지역 검색, 거리순 정렬, **내 프로그램을 몇 % 할 수 있는지** 함께 계산
- 전환 전에 무엇을 못 하게 되고 무엇이 새로 되는지 비교해 보여줍니다

```
예시 피트니스 A (대형)      0km   종목 81개   프로그램 100%
예시 짐 B (동네)         1.42km  종목 67개   프로그램 100%
예시 바벨 클럽          2.09km  종목 48개   프로그램  57%  (불가: 머신 체스트프레스 …)
예시 호텔 피트니스          8km   종목 35개   프로그램  33%  (불가: 바벨 벤치프레스, 풀업 …)
```

디렉터리에 들어 있는 항목은 **구조를 보여주기 위한 예시**이고 실재하는 업체가 아닙니다. 실제 제품에서는 지도 API로 주변 시설을 받아오고 기구 목록은 사용자가 채우는 크라우드소싱으로 쌓입니다.

### 블록 유형 (`styles.ts`)

근비대 한 가지로만 돌리면 지루하고, 근력은 늘지 않으며, 한계를 확인할 기회가 없습니다. 반대로 매주 한계에 도전하면 몇 주 만에 무너집니다. **한계 돌파는 기분이 아니라 계획**이고, 이 표가 그 계획의 단위입니다.

| 블록 | 주 반복 | 목표 RIR | 휴식 | 볼륨 | 길이 |
|---|---|---|---|---|---|
| 근비대 | 6–10 | 3→2→2→1→1 | ×1.0 | ×1.0 | 5주 |
| 근력 | 3–5 | 3→2→2→1 | ×1.5 | ×0.7 | 4주 |
| 고밀도 (빡세게) | 8–12 | 2→1→1 | ×0.65 | ×1.15 | **3주** |
| 한계 돌파 | 1–3 | 2→1 | ×2.0 | ×0.5 | 2주 |
| 컨디셔닝 | 8–15 | 2→2→1 | ×0.4 | ×0.6 | 3주 |

고밀도 블록이 3주인 건 임의가 아닙니다. 그 이상은 회복이 따라오지 못합니다. 연속으로도 못 돌립니다.

**막는 게 아니라 이유를 알려줍니다.**

```
초보자 → 근력 · 고밀도 · 한계 돌파 잠김 ("자세가 잡히기 전에 저반복 고중량으로 가면 …")
디로드 전 → 한계 돌파 잠김 ("지금 시도하면 기록이 아니라 컨디션을 재는 셈입니다")
통증 3점↑ → 한계 돌파 · 고밀도 잠김
같은 블록 3연속 → 잠김 ("다른 블록을 한 번 거친 뒤 돌아오세요")
```

### 강도 기법과 한계 테스트 (`intensity.ts`)

**강도 기법**은 자극을 올리는 대신 피로를 더 크게 올립니다. 그래서 유효 세트와 피로를 **따로** 셉니다.

| 기법 | 유효 세트 | 피로 |
|---|---|---|
| 드롭세트 | ×1.5 | ×2.0 |
| 레스트 포즈 | ×1.6 | ×2.2 |
| 미오렙 | ×1.8 | ×2.0 |
| 클러스터 세트 | ×1.3 | ×1.3 |
| 길항근 슈퍼세트 | ×1.0 | ×1.1 |
| AMRAP 피니셔 | ×1.2 | ×1.5 |

쓸 수 있는 상황인지 먼저 봅니다 — MRV 초과 부위 금지, 디로드 주 금지, 관절 부하 큰 복합 동작 금지, 초보는 고립 운동만, 앞 세트에는 붙이지 않음.

**한계 테스트**는 워밍업 램프부터 시도까지 계획합니다.

```
고급자 · 스쿼트 추정 1RM 180kg · 디로드 직후
  워밍업  72.5 ×5 (40%) → 100 ×5 (55%) → 125 ×3 (70%) → 145 ×2 (80%) → 157.5 ×1 (88%)
  시도    175kg (감각) → 180kg (추정치) → 187.5kg (2차가 깔끔했을 때만)
  ⚠ 시도는 세 번까지입니다. 네 번째는 이미 떨어진 능력을 재는 것입니다.
```

단계별로 테스트 반복이 다릅니다 — **초보 5RM, 중급 3RM, 고급 이상 1RM.** 초보에게 1RM 시도는 위험합니다.

### 컨디셔닝 (`conditioning.ts`)

크로스핏 스타일 세션입니다. AMRAP · EMOM · For Time · 인터벌 · 서킷.

**근비대 볼륨 회계와는 다른 물건입니다.** AMRAP 12분에서 나온 스쿼트 60회를 유효 세트로 세면 볼륨 처방이 전부 망가집니다. 그래서 유효 세트로는 세지 않고 **피로에만** 더합니다.

안전 규칙 하나가 특히 중요합니다 — **시간에 쫓기는 상태에서는 척추에 최대 부하가 실리는 동작을 넣지 않습니다.** 피로한 상태의 데드리프트는 컨디셔닝이 아니라 부상 대기입니다.

간섭도 봅니다: 하체 컨디셔닝 다음 날 하체 근력 세션이 있으면 경고하고, 같은 날이면 근력을 먼저 하라고 알려줍니다.

### RIR 신뢰도 보정 (`rirCalibration.ts`)

엔진 전체가 사용자가 신고한 RIR 위에 서 있는데, 그 신고가 정확하다는 보장이 없습니다. 초보자는 "3회 남았다"면서 실제로는 실패 직전인 경우가 흔하고, 그대로 믿으면 엔진이 중량을 계속 올려 실패 지점을 넘깁니다.

정답은 알 수 없지만 **기준점은 있습니다 — 실제로 실패까지 간 세트(RIR 0)**입니다.

```
실패 세트: 벤치 80kg × 8회  →  능력치 확정
신고 세트: 벤치 80kg × 8회 "RIR 3"  →  실제로는 RIR 0이었다
                                      → 편향 -3
```

| 판정 | 결과 |
|---|---|
| 과대 신고 | 음수 보정 — **증량을 막아 준다** |
| 정확 | 보정 ≈ 0, 신뢰도 100% |
| 과소 신고 | 양수 보정 — 아직 여유가 있다 |
| 기준 세트 없음 | 보정하지 않고, 가끔 실패까지 가 보라고 안내 |

기준 세트가 3개 미만이면 계산만 하고 **적용하지 않습니다.** 표본이 얕은데 건드리면 더 나빠집니다. 보정이 들어가면 처방 근거에 `RIR 3→1(보정)`처럼 그 사실을 표시합니다 — 사용자 몰래 숫자를 바꾸지 않습니다.

보정값은 유효 세트 집계(`volume.ts`)와 중량 처방(`load.ts`) 양쪽에 적용됩니다.

### 반복 대비 강도 (`repmax.ts`)

Epley 식 `w × (1 + reps/30)`은 선형이라 고반복 구간에서 능력을 과대 추정합니다. 8회 실패한 사람의 1RM은 맞게 나오지만, 거기서 15회 가능한 중량을 역산하면 실제보다 무겁게 나옵니다. RIR 보정처럼 **서로 다른 반복 구간을 비교하는 계산에서는 이 오차가 그대로 편향**이 됩니다.

그래서 현장에서 쓰는 %1RM 표를 씁니다. 정직하게 신고하는 사람에게 +1의 가짜 편향이 나오던 문제가 이걸로 사라졌습니다.

### 주간 스케줄 (`schedule.ts`)

요일 배치와 세션 순서를 따로 풀지 않고 같이 풉니다. 같은 부위를 이틀 연속 때리면 회복이 안 되는데, 그건 요일만 봐서도 세션 내용만 봐서도 알 수 없기 때문입니다.

- 훈련일을 한쪽에 몰지 않고 주에 고르게 폅니다 (주 3회 → 월·수·금)
- 가능한 요일을 지정하면 그 안에서 가장 고르게 펴진 조합을 고릅니다
- 붙어 있는 날에 같은 부위가 겹치지 않도록 세션 순서를 정합니다
- 연속 훈련일이 단계 권장(초보 2일, 그 외 3일)을 넘으면 경고합니다

### 워밍업 (`warmup.ts`)

빈 바로 10회 하고 바로 100kg으로 가는 건 워밍업이 아니라 도박이고, 본세트 전에 다섯 세트씩 밟으면 정작 본세트에서 쓸 힘이 남지 않습니다.

```
스쿼트 본세트 140kg × 5회 (첫 종목)
  20kg × 10회  (빈 바)   55kg × 8회   85kg × 5회   105kg × 3회   122.5kg × 2회

인클라인 덤벨프레스 30kg × 10회 (가슴이 이미 데워짐)
  14kg × 6회   22kg × 3회

트라이셉스 푸시다운 40kg × 12회 (삼두가 이미 데워짐)
  (없음 — 첫 세트를 여유 있게 시작)
```

- 무거워질수록 반복을 줄입니다
- 바벨 종목은 빈 바부터, 본세트가 빈 바에 가까우면 생략
- 앞 종목이 이미 데운 부위는 짧게 끝내거나 아예 건너뜁니다
- 기구에서 만들 수 있는 중량으로 맞춥니다
- **워밍업은 절대 실패까지 가지 않습니다** — 볼륨 집계에서도 빠집니다

### 자동 세트 수 (`autoregulation.ts`)

계획서에 "4세트"라고 적혀 있어도 그날 컨디션에 따라 3세트가 맞을 수도, 5세트가 맞을 수도 있습니다. 기준은 감이 아니라 **수행**입니다.

| 상황 | 판단 |
|---|---|
| 첫 세트 대비 반복 30% 이상 하락 | **멈춤** — "이 뒤는 자극이 아니라 피로만 쌓습니다" |
| 실패 지점인데 목표 하단도 미달 | 멈춤 |
| 그 부위가 이미 MRV 초과 | 최소 세트만 하고 멈춤 |
| 남은 시간이 한 세트에 못 미침 | 멈춤 |
| 계획 완료 + 마지막 세트 RIR 여유 2 이상 | **한 세트 더** 권함 |
| 계획 완료 + 여유 없음 | 계획에서 종료 |

"알아서"의 절반은 줄이는 것이고 나머지 절반은 늘리는 것입니다. RIR 보정도 여기에 반영되어, 실제보다 여유 있게 신고하는 사람에게 세트를 더 권하지 않습니다.

### 시간 예산 (`timeBudget.ts`)

"오늘 45분밖에 없다"가 가장 흔한 제약인데 대부분의 앱은 받아주지 않습니다. 그래서 사용자가 알아서 뒤쪽 종목을 건너뛰고, 그러면 주간 볼륨 계산이 틀어집니다.

**자르는 순서가 중요합니다.**

```
1. 고립 운동 세트  →  2. 고립 운동 제거  →  3. 보조 운동 세트
4. 보조 운동 제거  →  5. 메인 복합 세트 (최소 2세트 보장)
```

**메인 복합 동작은 통째로 빼지 않습니다.** 그게 빠지면 오늘 세션을 한 의미가 없습니다.

```
상체 A 예상 45분 (워밍업 9 · 수행 20 · 휴식 12 · 이동 6)
  40분 예산 → 38분  고립 세트 3건 축소
  30분 예산 → 28분  고립 2종목 제외 + 보조 세트 축소
  25분 예산 → 23분  고립·보조 4종목 제외, 메인 2종목은 유지
```

휴식을 1분 ~ 1분 30초 띠로 줄이면서 **휴식이 차지하는 몫이 크게 줄었습니다.** 예전에는 휴식이
수행 시간보다 컸지만 지금은 아닙니다 — 그래도 4분의 1 이상은 휴식이라, 시간을 맞출 때 휴식부터
건드리는 순서는 그대로입니다.

고밀도 블록에서는 종목을 빼기 전에 **휴식 단축**을 먼저 씁니다 (그 블록의 목적이 밀도이므로).

### 휴식 시간 (`rest.ts`)

볼륨을 관리하면서 휴식을 안 다루면 앞뒤가 안 맞습니다. 90초 쉬고 한 4세트와 3분 쉬고 한 4세트는 같은 4세트가 아닙니다.

**띠는 1분 ~ 1분 30초입니다.** 1분 아래로 내려가면 복합 동작에서 뒤 세트가 확실히 무너지고,
1분 30초를 넘기면 한 세션이 늘어져서 **아무도 안 지킵니다.** 이 두 값이 현장 판단이고, 아래
계산은 그 안에서 어디에 둘지만 정합니다.

| 조건 | 휴식 |
|---|---|
| 고립 운동 | 60초 |
| 복합 · 6회 이하 | 75초 |
| 복합 · 7~12회 | 70초 |
| 복합 · 13회 이상 | 60초 |
| 목표 RIR ≤ 1 | +10초 |
| 허리 부담 0.8 이상 | +10초 |
| 마지막 세트 | ×0.7 (최소 45초) |

조건이 겹쳐도 **90초를 넘기지 않습니다.** 넘기기 시작하면 결국 옛날처럼 3분이 되기 때문입니다.

여기 값은 **근비대 기준**이고, 블록 유형이 배수로 늘리고 줄입니다. 그래서 좁은 띠 하나만 지키면
나머지는 알아서 따라옵니다 — 여기서 3분을 주면 근력 블록이 4분 반이 됩니다.

| 블록 | 배수 | 데드리프트 8회 RIR2 |
|---|---|---|
| 근비대 | ×1 | 1:20 |
| 근력 | ×1.5 | 2:00 |
| 고밀도 | ×0.65 | 0:52 |
| 한계 돌파 | ×2 | 2:40 |
| 컨디셔닝 | ×0.4 | 0:32 |

타이머에는 **−30초 · +30초 · 건너뛰기**가 있습니다. 빼다가 남은 시간이 없어지면 타이머를
그냥 닫습니다 — 0초짜리를 띄워 두는 것보다 다음 세트로 넘어가는 게 사용자가 원한 것입니다.

### 오프라인 저장 (`storage.ts`)

헬스장 지하에는 신호가 없습니다. 서버를 기다리지 않고 로컬에 먼저 쓰고, 보낼 것들을 아웃박스에 쌓았다가 연결되면 흘려보냅니다.

- 모든 기록이 `id` · `updatedAt` · `deviceId`를 갖습니다
- 충돌은 **마지막 수정 시각**으로 해결하고, 같으면 기기 id로 순서를 정해 **어느 기기에서 보든 같은 결과**가 나옵니다
- 삭제는 표시만 남깁니다 — 실제로 지우면 다른 기기가 자기 사본으로 되살립니다
- 저장소가 막힌 환경(시크릿 창)에서도 앱이 죽지 않습니다

### 개인 볼륨 랜드마크 (`personalization.ts`)

MEV·MAV·MRV는 개인차가 가장 큰 값입니다. 같은 중급자라도 가슴 MRV가 16인 사람과 26인 사람이 있습니다.
정답은 알 수 없지만 관측은 할 수 있습니다. 8주 이상 쌓이면 그 사람의 기록이 직접 말하게 합니다.

관측은 **등식이 아니라 부등식**입니다. 이걸 한 번 틀렸습니다 — "12세트 하고 성장했다"를 "MEV는 12다"로
읽으면, 잘 회복하는 사람일수록 최소 자극선이 올라가는 거꾸로 된 결과가 나옵니다. 그래서 세 방향만 인정합니다.

| 관측 | 말해주는 것 | 움직이는 방향 |
| --- | --- | --- |
| 볼륨 V에서 다음 주 수행력 하락 | MRV < V | V가 지금 MRV보다 낮을 때만 MRV를 내림 |
| 볼륨 V에서 수행력 유지·상승 | MRV ≥ V | V가 지금 MRV보다 높을 때만 MRV를 올림 |
| 볼륨 V에서 성장 | MEV ≤ V | V가 지금 MEV보다 낮을 때만 MEV를 내림 |

MEV를 올리려면 "이 볼륨으로는 자라지 않았다"는 반대 증거가 필요한데, 지금 기록으로는 자극 부족과 컨디션을
구분할 수 없습니다. 그래서 **MEV는 내리기만 합니다.**

회복 실패의 책임도 모든 부위에 똑같이 물리지 않습니다. 가슴을 20세트 하고 무너졌는데 1세트 한 삼두의 MRV를
내리는 건 틀렸습니다. 그 주에 랜드마크 대비 부하가 가장 컸던 **두 부위만** 원인으로 지목하고, 그마저도
절대 하한(`blameFloor`)을 넘긴 부위에 한합니다.

반영 비율은 관측 횟수에 따라 30%에서 시작해 최대 60%까지입니다. 관측 2회와 7회를 같은 무게로 볼 수는
없지만, 한 사람의 기록으로 교과서 값을 통째로 대체하지도 않습니다.

세트는 정수이므로, 30%를 섞어도 반올림에 묻혀 숫자가 그대로 남는 경우가 많습니다. 그때 "개인값으로
옮겼습니다"라고 말하면 거짓말이 되므로 **실제로 바뀐 부위만** 옮겼다고 셉니다. 나머지는 "관측 중"으로 둡니다.

### 동작 시연 (`demos.ts`)

83개 종목에 시연이 하나도 없으면 초보자는 "랜드마인 프레스"가 뭔지 모릅니다.
실제 제품에서는 촬영 영상이나 구매한 3D 에셋이 들어갈 자리인데, 지금은 관절 각도 키프레임으로 절차적
애니메이션을 돌려 그 자리를 채웁니다.

구조를 이렇게 잡은 이유가 있습니다 — 종목마다 에셋을 만들면 83개를 다 찍어야 하지만, **동작 패턴 10개**로
묶으면 10개만 만들고 종목별로는 큐와 실수만 덧붙이면 됩니다. 나중에 실제 에셋으로 교체할 때도 패턴 단위로
갈아끼웁니다. 현재 17개 종목에 맞춤 큐가 있고, 나머지는 패턴 기본값을 씁니다.

서 있는 자세는 다리 기하에서 골반 높이를 역산해 **발이 항상 바닥에 닿습니다**(`groundedDrop`).
골반을 고정해두면 무릎을 굽힐수록 발이 공중으로 떠올라, 스쿼트가 앉은 자세로 보입니다.
플랭크 같은 등척성 종목은 코어 패턴(크런치)이 아니라 버티기 키프레임을 따로 씁니다.

렌더러(`prototype/demo3d.js`)는 three.js가 있으면 3D로, 없으면 **같은 키프레임을 2D 캔버스로** 그립니다.
관절 회전이 전부 X축이라 옆모습에는 손실이 없습니다.

### 세션 요약 (`summary.ts`)

운동을 마치고 나면 "오늘 뭘 했지"가 남아야 합니다. 세트 목록만 보여주면 그날의 의미를 알 수 없습니다.
오늘 한 것이 주간 계획의 어디쯤인지, 무엇이 늘었는지, 다음 주가 어떻게 달라지는지가 요약의 내용입니다.

- 세트·반복·톤수, 오늘 최고 수행(추정 1RM)
- 부위별 **오늘 / 이번 주** 누적과 구간 판정
- 오늘 깬 개인 기록, 올린 중량
- 다음 주 처방 요약

없는 성과를 억지로 만들지 않습니다. 중량이 그대로면 아무것도 쓰지 않습니다.

### 얼마나 자주 오는가 (`onboarding.ts`)

주 1회부터 7회까지 받습니다. 다만 **되는 척하지 않습니다.**

| 일수 | 분할 | MEV 미달 부위 |
| --- | --- | --- |
| 1 | 전신 1회 | 7 / 14 |
| 2 | 전신 2회 | 5 / 14 |
| 3 | 전신 3회 | 3 / 14 |
| 4 | 상하체 분할 | 2 / 14 |
| 5 | 혼합 분할 | 2 / 14 |
| 6 | 푸시·풀·레그 2순환 | 2 / 14 |
| 7 | + 보완일 | 0 / 14 |

주 1회로는 대부분의 부위가 최소 자극선에 닿지 않습니다. 그걸 숨기고 "훌륭한 프로그램입니다"라고 하면
몇 달 뒤에 사용자가 앱을 탓하게 됩니다. **주 1회는 늘리는 일정이 아니라 지키는 일정**이라고 처음에
말합니다(`program.caution`).

7일째는 또 하나의 하드 세션이 아니라 약한 부위만 채우는 **보완일**입니다. 매일 고강도로 하면 회복이
안 되고, 이런 날이 있어야 나머지 6일을 제대로 합니다.

### 체중은 쓰고 키는 받지 않는다

체중은 세 곳에서 실제로 씁니다.

- **첫날 중량** — 이력이 하나도 없을 때 `체중 × 경력별 비율 × 성별 계수`로 출발점을 뽑습니다(`strength.ts`)
- **경력 검증** — 신고한 단계와 `1RM ÷ 체중` 비율을 대조해 과대 신고를 잡습니다(`levels.ts`)
- **맨몸 종목** — 풀업·딥스의 부하가 체중입니다

키는 **어디에도 쓰지 않아서 받지 않습니다.** 가동범위나 종목 선택에 끼워 넣을 수는 있지만 개인차가
커서 규칙으로 박으면 틀린 처방이 나옵니다. 건강정보는 최소수집이 원칙이고, 안 쓸 데이터를 받아둘
이유가 없습니다.

### 머신 중량 (`gymWeight.ts`)

바벨 100kg은 어디서나 100kg입니다. 그런데 **레그프레스 100kg은 그렇지 않습니다** — 기계마다 썰매 각도와
카운터웨이트가 달라 실제 부하가 20~30% 차이납니다. 케이블은 도르래 비율이 2:1인 기계와 1:1인 기계가
섞여 있고, 스미스머신은 바 자체가 7kg짜리도 25kg짜리도 있습니다.

세 곳을 다니는 사람에게 이걸 무시하면 A짐에서 쌓은 100kg 기록을 들고 B짐에 가서 엉뚱한 무게로
시작합니다. 너무 가벼우면 한 세션을 버리고, **너무 무거우면 다칩니다.**

그래서 중량 이력을 종목이 아니라 **종목 × 헬스장**으로 봅니다. 다만 전부 나누면 안 됩니다 — 바벨과
덤벨까지 나누면 헬스장을 옮길 때마다 처음부터 시작하게 되고, 그건 사실과 다릅니다.

| 기구 | 이력 |
| --- | --- |
| 바벨 · 덤벨 · 맨몸 | 전부 본다 |
| 머신 · 케이블 · 스미스 · 밴드 | **같은 헬스장 기록만** |

그 헬스장에 기록이 없으면 "첫 수행"으로 보고 다른 종목에서 환산해 출발점을 잡습니다(`strength.ts`).
그리고 **처음 쓰는 기계라는 사실을 숨기지 않습니다** — "다른 곳에서 100kg 했지만 이 기계는 처음"이라고
말해줘야 사용자가 첫 세트에서 확인합니다.

### 목표 조합 (`goals.ts`)

"근비대도 하고 근력도 늘리고 체지방도 빼고 싶다"가 현장에서 가장 많이 듣는 말입니다. 앱들은 보통
하나만 고르게 하고 끝내는데, 그건 사용자가 실제로 원하는 것을 못 담습니다. **여러 개를 고를 수 있게 하되,
무엇이 무엇을 깎는지 숨기지 않습니다.**

| 조합 | 처방 |
| --- | --- |
| 근력 + 근비대 | 메인은 저반복(4~6), 보조·고립은 중반복 |
| + 체지방 감량 | 반복 범위는 **그대로**, 볼륨 상한만 MRV → MAV |

**체지방 감량은 반복 범위를 바꾸지 않습니다.** "고반복이 커팅"은 오래된 오해이고, 적자에서 고반복으로
바꾸면 강도가 떨어져 오히려 근육을 잃습니다. 체지방은 식사에서 빠지고, 훈련에서 할 일은 근육을 지키는
것이며, 그건 중량을 유지할 때 됩니다. 대신 적자에서는 회복이 느려지므로 **볼륨을 MRV까지 밀지 않고
MAV에서 멈춥니다.**

### 헬스장 신원 (`gymIdentity.ts`)

A가 "상구헬스장"을 등록했는데 B가 "상구 헬스장"으로 다시 만들면 같은 곳의 기구 정보가 두 벌로 쪼개집니다.
다섯 명이 각자 반쪽짜리를 채우면 **크라우드소싱은 그대로 죽습니다.**

그렇다고 마구 합치면 더 나쁩니다. 미병합은 불편할 뿐이지만 **과병합은 없는 기구로 처방이 나가서
사용자가 헬스장에 가서 못 합니다.** 그래서 애매하면 합치지 않고 사람에게 묻습니다.

판정의 축은 이름이 아니라 **위치**입니다. 같은 이름 다른 곳("헬스킹"은 전국에 여럿)과 다른 이름 같은
곳(간판이 바뀌거나 사람마다 다르게 기억합니다)이 둘 다 흔하기 때문입니다.

판정 순서 — **층과 지점을 거리보다 먼저** 봅니다.

| 조건 | 판정 |
| --- | --- |
| 층이 다름 | **다른 곳** — 좌표가 0m여도. 같은 건물 3층과 5층은 다른 헬스장입니다 |
| 지점이 다름 | **다른 곳** — 수원점과 이천점은 바로 옆에 있어도 다릅니다 |
| 50m 이내 + 이름 0.6↑ | 같은 곳 |
| 50m 이내 + 이름 낮음 | 후보 — 같은 건물의 다른 헬스장일 수 있습니다 |
| 200m 이내 + 이름 0.9↑ | 같은 곳 — 실내에서는 위치가 이만큼 튑니다 |
| 600m 이내 + 이름 완전 일치 | 후보 |
| 한쪽만 층·지점을 밝힘 | 후보 — 자동으로 합치지 않습니다 |

**이름 비교는 브랜드로 합니다.** "상구헬스장"과 "상구피트니스"를 통째로 비교하면 0.2가 나옵니다 —
시설 접미사가 달라 글자가 안 겹치기 때문인데, 실제로는 간판만 바꾼 같은 곳인 경우가 훨씬 많습니다.
브랜드끼리 비교해야 "상구" = "상구"가 보입니다.

띄어쓰기가 없어도 가릅니다. **시설 접미사가 칼**입니다 — "상구헬스장수원점"에서 '헬스장'을 찾으면
앞은 브랜드(상구), 뒤는 지점(수원)입니다. 접미사가 없는 프랜차이즈("스포애니강남점")는 '점' 앞부분을
통째로 비교합니다.

**id는 좌표와 이름에서 결정적으로 만듭니다.** 시각+난수로 만들면 A와 B가 같은 곳을 등록해도 영원히
다른 id를 갖고, 서버가 붙는 순간 합칠 근거가 사라집니다. 좌표를 110m 격자로 반올림하고 브랜드·지점·층을
섞으면 각자 등록해도 같은 값이 나옵니다.

### 헬스장 등록과 병합 (`gyms.ts`)

`registerGym()`을 거치지 않으면 새 항목을 만들 수 없게 했습니다. 세 갈래로만 끝납니다.

- **joined** — 확실히 같은 곳이 있습니다. 그걸 씁니다
- **confirm** — 비슷한 게 있습니다. **사용자가 고르기 전에는 만들지 않습니다**
- **created** — 겹치는 게 없거나, 사용자가 "아니다"라고 했습니다

기구 정보를 합칠 때는 **합집합이 아니라 최근 확인이 이깁니다.** A가 3월에 "레그프레스 있음"이라
했고 B가 9월에 "없음"이라 했으면 없는 것입니다. 합집합으로 합치면 없어진 기구가 영원히 남습니다 —
한 번 "있음"이 들어가면 누구도 지울 수 없게 됩니다. 그래서 `absentEquipmentIds`(없다고 확인된 기구)를
따로 둡니다.

**헬스장은 공용 레코드입니다.** A가 등록했다고 A의 것이 아닙니다. 개인이 갖는 건 "내가 다니는 목록"
(`GymBook`)뿐이고, 기구 정보는 누구나 고치되 최근 확인이 이깁니다. 그래서 B는 "다시 등록"이 아니라
"내 목록에 추가"를 하게 되고, 애초에 중복을 만들 이유가 사라집니다.

### 기구 이름을 몰라도 (`equipment.ts`)

"올림픽 바벨 + 플레이트"나 "펙덱"이 뭔지 모르는 사람이 훨씬 많습니다. 이름만 늘어놓고 고르라고 하면
초보자는 거기서 앱을 닫습니다. 그래서 기구마다 **다르게 부르는 이름과 생김새**를 같이 둡니다.

```
펙덱 (플라이 머신)
  앉아서 양팔을 안으로 모으는 기계. 나비처럼 생겼습니다
  또는 펙덱 · 플라이 머신 · 나비 기계
```

검색은 **낱말 단위**입니다. "굽은 봉"을 통째로 붙여 찾으면 "가운데가 W자로 굽은 짧은 봉"에서 못
찾습니다 — 사람은 기억나는 낱말 몇 개만 던집니다.

| 친 말 | 나오는 것 |
| --- | --- |
| 굽은 봉 | EZ 바 |
| 나비 | 펙덱 |
| 철장 | 파워랙 |
| 줄 당기는 | 케이블 스테이션 |
| 다리 미는 | 레그프레스 |
| 레일 | 스미스머신 |

그래도 모르겠으면 **"잘 모르겠어요 — 나중에 할게요"**로 넘어갑니다. 어느 헬스장에나 있는 11개만 켜고
시작하고(종목 59개), **실측 단계까지 건너뜁니다** — 기구를 모르겠다는 사람에게 "빈 바 무게가 몇
kg인가요"를 묻는 건 더 모르는 걸 묻는 것입니다. 한국 헬스장은 대부분 빈 바 20kg · 스택 5kg이라
기본값이 거의 맞고, 틀리면 헬스장 탭에서 고치면 됩니다.

### 이름 옆에 그림 (`prototype/equipmentArt.js`)

글로 된 설명은 "이게 그거 맞나"를 끝까지 확인해 주지 못합니다. 눈앞에 기계가 있는데도 **플랫 벤치와
인클라인 벤치** 중 어느 쪽인지 헷갈리는 게 실제로 벌어지는 일입니다. 그래서 기구 31개 전부에 그림을
붙였습니다 — 이름, 생김새 설명, 그림 세 개가 한 줄에 같이 섭니다.

**사진 대신 선화(線畫)를 직접 그렸습니다.** 이유가 셋입니다.

1. **저작권.** 웹에서 긁어오면 안 되고, 스톡은 기구 한 대에 몇 달러씩 듭니다. 31개면 비용도 비용이지만
   재라이선스 관리가 따라붙습니다.
2. **헬스장마다 색과 브랜드가 다릅니다.** 사진 한 장은 그중 한 대만 보여주는데 사용자 눈앞의 기계는
   색이 다릅니다. 오히려 헷갈립니다.
3. **알아보는 데 필요한 건 실루엣입니다.** 레그프레스는 "비스듬한 레일에 발판"이고, 그건 선 몇 개로
   충분합니다.

기술적으로도 선화가 낫습니다. `currentColor`로 그려서 **다크 모드가 자동으로 따라오고, 고른 줄에서는
강조색으로 바뀝니다.** 확대해도 깨지지 않고, 31개를 다 합쳐도 8KB가 안 돼서 한 장짜리 HTML에 그대로
들어갑니다.

그림을 그릴 때 신경 쓴 건 **헷갈리는 것끼리 갈라 두는 것**입니다. 숄더프레스·펙덱·레터럴 레이즈는
전부 "앉아서 팔을 쓰는 기계"라 처음 그렸을 때 셋 다 같은 Y자로 나왔습니다. 손잡이가 머리 위로
올라가는 것(숄더프레스), 가슴 높이에서 앞으로 모이는 것(펙덱), 팔꿈치 패드가 옆으로 벌어지는
것(레터럴 레이즈)으로 나눠 다시 그렸습니다. 백 익스텐션대와 랜드마인도 둘 다 "비스듬한 막대"라
겹쳤는데, 백 익스텐션대에 **발목 롤러 두 개**를 그려 넣어 갈랐습니다.

테스트가 짝을 지킵니다 — 카탈로그에 기구를 추가하고 그림을 잊으면 `equipmentArt.test.ts`가 잡고,
색을 하드코딩하거나 좌표가 viewBox(64×48)를 넘어도 잡습니다.

나중에 실제 촬영본이나 라이선스 사진으로 바꾸고 싶으면 **표의 값만 `<img>`로 갈아끼우면 됩니다.**
부르는 쪽(`equipArt(id, name)`)은 그대로입니다.

### 세트도 한 번에 하나 (`app.js`)

종목을 하나씩 보여주고 나니 **그 안에서 같은 문제가 또 나왔습니다.** 6세트를 다 펼쳐 놓으면
`60kg 목표 6–10회`가 여섯 줄 쌓입니다. 전부 똑같이 생겼습니다. 화면에서 스크롤을 잃고,
지금 몇 세트째인지 **세어 봐야** 압니다. 숨차는 채로 할 일이 아닙니다.

```
● ● ○ ○ ○ ○                    3 / 6 세트
워밍업  4세트 · 약 5분                  펼치기
완료   2세트                              보기
────────────────────────────
3세트
105 kg                         목표 6–10회
20kg + 한쪽 25 · 15 · 2.5
반복                         [ − ] 10회 [ + ]
RIR   [실패] [1] [2] [3] [4]
```

- **점이 세트입니다.** 세어 볼 필요가 없습니다. 정확히 알아야 할 때를 위해 옆에 `세트 3 / 6`을
  같이 둡니다 — 중량 다음으로 자주 보는 숫자인데 처음엔 11px 회색 잔글씨였습니다.
- **세트 수를 한 화면에서 두 번 세지 않습니다.** 판단 줄이 "2/6세트"라고 말하고 머리글이
  "세트 3 / 6"이라고 말하면, 완료 기준과 현재 기준이 섞여 어느 게 맞는지 모르게 됩니다.
  숫자는 한 곳에서만 말하고, 판단 줄은 "그래서 계속해도 되나"만 말합니다.
- **`이전`이 아니라 `← 이전 종목`입니다.** "이전"만 있으면 세트 얘긴지 종목 얘긴지 모릅니다.
  `다음 종목`과 짝을 맞췄습니다.
- **끝난 세트는 접어 둡니다.** 기록을 고칠 일은 있어도 늘 보일 필요는 없습니다. `고치기`를
  누르면 되돌아가고, **주간 볼륨에서도 같이 빠집니다** — 화면만 되돌리고 기록이 남으면
  볼륨이 부풀어서 다음 주 처방이 틀어집니다.
- **워밍업은 첫 본세트를 하면 접힙니다.** 4세트짜리 램프가 계속 펼쳐져 있으면 정작 지금 할
  세트가 화면 밖으로 밀립니다. 직접 펼친 경우는 그대로 둡니다.
- **중량과 반복은 직접 칩니다.** ± 버튼만 두면 105에서 60으로 내리는 데 열여덟 번을 눌러야 합니다.
  처방과 다르게 한 날이 오히려 기록이 중요한 날인데, 그때 입력이 번거로우면 **아예 기록을 안 합니다.**
  버튼은 미세 조정용으로 남겼습니다.
- **± 한 번은 "한 칸"이지 "2.5kg"가 아닙니다.** 덤벨은 간격이 일정하지 않습니다(20, 22.5, 25, 30…).
  증분을 더하면 그 헬스장에 없는 무게가 나옵니다. `neighborLoad()`가 만들 수 있는 무게 목록에서
  한 칸 옮깁니다. 끝에 닿으면 그 자리에 둡니다.
- **못 만드는 무게를 쳐도 고쳐주지 않습니다.** `103kg — 이 헬스장 기구로는 만들 수 없는 무게입니다`라고
  알려주고, 누르면 102.5kg로 맞춰집니다. 다른 바를 쓰거나 눈금이 다른 기계일 수도 있고, 그건
  사용자가 더 잘 압니다.
- **RIR 칩을 키웠습니다.** 40px 이상 — 땀난 손, 장갑 낀 손으로 눌러야 합니다.

### 운동한 시간 (`app.js`)

`운동 12:34` — 시작하기를 누른 순간부터 잽니다. **화면 위에 고정**돼 스크롤해도 사라지지 않습니다.
몇 종목째인지와 얼마나 했는지는 세트를 내려다보는 중에도 보여야 하는 정보입니다. 폰 시계는 "몇 시"만 알려주지 **"얼마나 했는지"는
모릅니다.** 헬스장에서 제일 자주 하는 질문인데 앱이 답을 안 해줬습니다.

남은 시간을 세는 대신 **시작한 시각을 저장**해두고 매번 지금과 뺍니다. 화면이 꺼져 있던 동안도
정확하고, 앱이 다시 떠도 이어집니다. 1초마다 **숫자 하나만** 바꿉니다 — 화면 전체를 다시 그리면
RIR을 누르는 중에 버튼이 밀립니다.

### 끝나고 나서야 요약 (`app.js`)

"세션 완료 · 2세트 요약 보기"가 **운동 중에 계속 떠 있었습니다.** 3세트째에 화면에서 제일 큰
버튼이 "세션 완료"면 다음에 뭘 해야 하는지 잘못 읽힙니다. 지금 할 일은 다음 세트고, 요약은
다 끝나고 볼 것입니다.

- **마지막 종목의 마지막 세트까지 끝났을 때만** 완료 버튼이 뜹니다 (`오늘 운동 완료 · 요약 보기`).
- 시간이 없어 중간에 끝내야 하는 날도 있으므로 길은 막지 않습니다. 그건 **목록 화면**에
  `여기서 끝내기 · N세트 요약`으로 조용히 둡니다.
- **종목의 세트를 다 하면 다음 종목으로 자동으로 넘어갑니다.** 헬스장에서는 끝나면 다음 기구로
  걸어갑니다 — 화면이 그 자리에 머물러 있으면 사용자가 버튼을 찾아 눌러야 하는데, 그건 앱이
  할 일입니다. 휴식 타이머는 화면 아래에 계속 있으므로 걸어가면서 쉬면 됩니다.
  다만 **"한 세트 더" 판단이 붙었으면 안 넘깁니다** — 그걸 물어보려고 계산한 것인데 화면을
  넘겨버리면 물어볼 기회가 사라집니다.
- **요약을 닫으면 아무 데도 안 가는 것도 문제였습니다.** `오늘 마치기`로 세션을 닫고, 그 뒤에는
  목록 대신 "오늘 운동을 마쳤습니다" 화면이 나옵니다. 잘못 눌렀을 수 있으니 `이어서 하기`로
  되돌아갈 수 있습니다.
- **완료 버튼이 컨디셔닝 시트 아래에 묻혀 있었습니다.** 마지막 종목을 끝냈는데 남은 게 `이전`
  하나뿐이면 막다른 길처럼 보입니다 — 다음 행동이 스크롤 두 번 아래에 있으면 "아무 일도 안
  일어난다"로 읽힙니다. 완료 버튼을 컨디셔닝·맥스테스트 **위로** 올렸고, `이전`은 좁게 줄였습니다.
- **끝난 종목에 강도 기법을 계속 띄우지 않습니다.** 그건 "마지막 세트에 붙일" 것이라 세트를 다
  기록한 뒤에는 할 일이 남은 것처럼 보이고, 정작 완료 버튼을 화면 밖으로 밀어냅니다.

### 브라우저 확인창을 쓰지 않는다 (`app.js`)

`window.confirm`으로 "오늘 기록이 지워집니다, 바꿀까요?"를 물었는데, **아티팩트에서 날을 바꾸는
기능이 통째로 먹통이었습니다.** 눌러도 아무 일이 안 일어났습니다.

원인은 샌드박스입니다. 앱이 iframe 안에서 돌면(아티팩트, 웹뷰, 일부 인앱 브라우저) `confirm`은
**뜨지도 않고 조용히 "취소"로 처리**됩니다. 그러면 코드는 `if (!ok) return;`에서 빠져나가고,
사용자에게는 버튼이 고장난 것으로 보입니다.

물어볼 게 있으면 **앱 안 모달**로 묻습니다. `confirm`·`alert`·`prompt`를 쓰지 않는지
테스트가 지킵니다 — 기능 테스트로는 안 잡히고 실제 기기에서만 터지는 종류라서,
구조적으로 막아 둡니다. (`installEvent.prompt()`는 PWA 설치 프롬프트라 전혀 다른 것이므로
점 뒤는 세지 않습니다.)

같은 파일의 다른 금지 사항: **조사 자리표시자**(`을(를)`, `은(는)`)가 화면에 나가지 않는지도
같이 봅니다. 엔진의 `withParticle`을 쓰면 받침을 보고 고릅니다.

### 지난번과 비교 (`comparison.ts`)

"오늘 22세트 했다"는 끝나고 나면 아무 감흥이 없습니다. 알고 싶은 건 **늘었는가**이고,
그건 지난번의 나와 비교해야 나옵니다.

```
지난번 대비 3종목 올랐습니다 · 1종목 유지.

컨벤셔널 데드리프트      7일 전 100kg × 10회 → 오늘 환산 +7.5kg      +7.5kg
                        한 달 · 21일 전 100kg × 9회 → 환산 +20.5kg
레그프레스 카프레이즈    3일 전 102.5kg × 15회 → 그대로입니다        고반복
                        한 달 · 21일 전 102.5kg × 14회 → 같은 무게로 1회 더
```

**무게를 그냥 비교하면 안 됩니다.** 지난주 60kg 10회와 오늘 80kg 5회 중 어느 쪽이 나은지는
무게만 봐서는 모릅니다. 추정 1RM으로 환산해 재되, 환산값만 내보내지 않고 **실제로 든 세트를
같이 붙입니다.**

판단을 흐리지 않으려고 정한 것들:

- **무게가 같으면 환산을 꺼내지 않습니다.** `같은 무게로 1회 더`가 사실 그대로이고 훨씬 잘
  읽힙니다. 같은 무게·반복인데 RIR이 나빠졌으면 `더 힘들었습니다`라고 씁니다.
- **고반복에서는 환산을 믿지 않습니다.** 102.5kg 14회(RIR 0)와 15회(RIR 2)의 환산 차이는
  13.7kg인데, 실제로 달라진 건 "한 번 더 했다"뿐입니다. 이걸 "13.7kg 늘었다"고 말하면
  트레이너는 앱을 안 믿습니다. 유효 반복(반복+RIR)이 12를 넘으면 큰 kg 숫자 대신 `고반복`이라고
  표시하고 반복으로 말합니다.
- **2.5kg 미만은 "비슷하다"입니다.** 추정 1RM은 RIR 신고에 따라 1~2kg은 쉽게 흔들립니다.
  그 안의 변화를 성장이라 부르면 매주 늘었다고 말하게 되고, 그러면 아무도 안 믿습니다.
- **한 달 비교는 21~35일 창 안에서만** 합니다. 정확히 28일 전에 그 종목을 했을 확률은 낮고,
  두 달 전 기록을 "한 달 전"이라고 부르면 그건 거짓말입니다. 창 밖이면 `한 달 전 기록이 없습니다`.
- **내려간 종목을 감추지 않습니다.** 내려간 날을 감추면 올라간 날도 못 믿게 됩니다.
- **그 세션의 최고 세트만** 씁니다. 뒤 세트는 피로가 섞여 있어 능력의 변화가 아닙니다.

### 오늘 할 날을 바꾼다 (`dayChoice.ts`)

프로그램은 상체 A → 하체 A → 상체 B → 하체 B로 순환합니다. 그런데 **현장에서는 순서대로 안 옵니다.**
"오늘 상체 하고 싶다", "어제 못 와서 하체가 밀렸다", "다리가 아직 뻐근하다"가 매주 있습니다.

순서를 강제하면 사용자는 **앱을 무시하고 자기 마음대로 합니다.** 그러면 기록이 안 남고, 기록이
없으면 볼륨 계산도 처방도 전부 틀어집니다. 앱이 틀리는 것보다 나쁩니다.

그래서 막지 않습니다. 대신 **그 부위를 마지막으로 언제 했는지** 말합니다.

```
하체 B  [오늘 차례]   둔근 · 햄스트링 · 대퇴사두 · 종아리
                      둔근 마지막 3일 전. 회복됐습니다.
상체 A                가슴 · 삼두 · 전면 삼각근 · 이두
                      어제 가슴을 했습니다. 하루로는 회복이 덜 됩니다 — 다른 날을 먼저 하는 게 낫습니다.
```

판단을 흐리지 않으려고 정한 것들:

- **주요 부위 중 가장 최근 것을 봅니다. 평균이 아닙니다.** 하체 날에 둔근은 4일 전, 대퇴사두는
  어제라면 문제가 되는 건 대퇴사두입니다. 평균을 내면 "회복됐다"가 나와서 위험합니다.
- **스치기만 한 부위는 세지 않습니다.** 데드리프트의 대퇴사두는 0.3입니다. 이걸로 "어제 다리를
  했다"고 하면 경고가 아무 데서나 떠서 아무도 안 읽게 됩니다. 기여도 0.5 이상만 셉니다.
- **회복된 날이 목록 위로 옵니다.** 정렬이 곧 조언입니다 — 경고 문구를 읽지 않는 사람에게도
  전달됩니다. 조건이 같으면 원래 차례가 위로 갑니다. 이유 없이 프로그램을 흔들지 않습니다.
- **건너뛴 날은 없어지지 않고 다음으로 밀립니다.** 주간 볼륨은 한 주 전체로 계산하므로 순서가
  바뀌어도 목표는 그대로입니다. 그 말을 화면에 그대로 씁니다.
- 세트를 이미 기록했으면 **바꾸기 전에 물어봅니다.** 다른 날의 종목이 섞이면 어느 세션에 속한
  세트인지 알 수 없게 됩니다.

회복 기준은 48시간입니다. 평균값이고 사람마다 다르므로 막는 근거로는 쓰지 않습니다 —
실제 회복은 볼륨 게이지와 피로 신호가 따로 재고 있습니다.

### 순서 변경 (`reorder.ts`)

순서를 바꿀 이유는 늘 있습니다 — 랙에 사람이 있고, 오늘은 어깨부터 하고 싶고, 시간이 없어서
중요한 것부터 하고 싶습니다. **막을 이유가 없습니다.**

다만 순서가 아무래도 되는 건 아닙니다. 그래서 막지 않고 **말합니다.**

```
순서 주의
레그프레스 카프레이즈 다음에 컨벤셔널 데드리프트입니다.
허리가 지친 상태에서 하면 자세가 먼저 무너집니다. 앞으로 옮기세요.
```

**규칙을 정하다가 한 번 틀렸습니다.** 처음에는 "관절 부하가 큰 종목이 세 번째 이후면 경고"로
짰는데, **하체 날은 무거운 복합이 셋이라 프로그램이 짜 준 기본 순서가 자기 경고에 걸렸습니다.**
앱이 자기 처방에 경고를 띄우면 그 경고는 그때부터 배경 소음이고, 정작 위험할 때 아무도 안 읽습니다.

진짜 문제는 순번이 아니라 **무엇 다음에 오느냐**였습니다. 컬을 하고 데드리프트를 하는 게 위험한
것이지, 스쿼트를 하고 데드리프트를 하는 건 그냥 하체 날입니다.

**두 번째로 틀린 것:** 고친 규칙이 이번엔 `케이블 플라이 → 벤치프레스`를 위험하다고 했습니다.
그건 **선피로**라는 정상적인 기법입니다. 가슴이 지치면 드는 무게가 줄 뿐 다치지 않습니다.
피로 상태에서 실제로 위험해지는 건 **허리**입니다 — 자세가 무너지는 곳이 하필 제일 위험한
곳이기 때문입니다. 그래서 경고는 **허리 부하(`lowBack ≥ 0.7`)로만** 냅니다.

| 순서 | 판정 |
|---|---|
| 데드 → 스쿼트 → 스티프레그 → 카프레이즈 | 걸리는 것 없음 (기본 순서) |
| 컬 → 데드리프트 | **경고** — 허리가 지친 상태 |
| 카프레이즈 → 데드리프트 | **경고** — 같음 |
| 케이블 플라이 → 벤치프레스 | 참고 — 선피로 기법입니다 |

구현에서 챙긴 것들:

- **워밍업을 다시 잡습니다.** "앞 종목이 데운 부위는 짧게"가 순서에 달려 있으므로, 순서를
  적용한 **뒤에** 워밍업을 계산합니다.
- **바꾼 순서가 세션 재생성을 견딥니다.** 시간을 줄이거나 통증이 생기면 종목이 바뀌는데,
  그때 순서가 프로그램 기본으로 돌아가면 안 됩니다. 저장된 순서에 없는 종목은 뒤에 붙이고,
  사라진 종목은 무시합니다 — 순서를 한 번 바꿨다고 이후의 교체가 막히면 안 됩니다.
- **이미 기록한 세트는 따라갑니다.** 기록은 종목에 붙어 있고, 진행 중이었다면 보고 있던
  종목을 계속 봅니다.
- **끌어서 옮기지 않고 ↑↓ 버튼을 씁니다.** 땀난 손으로 스크롤하는 목록 위에서 끌기는 잘
  안 잡힙니다. 버튼은 눌리기만 하면 되고 키보드·스크린리더에서도 그대로 동작합니다.
- **되돌릴 길을 남깁니다.** `프로그램 순서로 되돌리기` — 하나씩 되돌리게 하면 아무도 안 씁니다.

### 시작 전 목록 (`app.js`)

시작 전 화면에서 제일 중요한 건 **"오늘 뭘 하는가"**입니다. 그런데 시간 설정 시트가 늘 펼쳐진
채로 목록 위를 차지하고 있었습니다.

위쪽은 **요약 카드 두 장**으로 접었습니다 — `운동 시간 57분` · `컨디션 80%`. 누르면 펼쳐집니다.

- **컨디션은 지어낸 숫자가 아닙니다.** 엔진이 계산하는 피로 점수를 뒤집은 값입니다
  (`100 - score/threshold × 100`). 펼치면 **왜 그 점수인지** 신호를 그대로 보여줍니다 —
  "둔근 볼륨이 회복 가능 범위(MRV)를 넘었습니다" 같은 것들입니다. 퍼센트만 던지면 근거를
  알 수 없습니다.

목록은 **썸네일 + 이름 + 처방** 한 줄입니다.

```
[▭]  컨벤셔널 데드리프트
     6세트 · 105kg · 6–10회                    ⋯
```

- **썸네일 자리에는 그 종목을 하는 기구를 그립니다.** 촬영본이 들어오면 영상 첫 프레임이 되고,
  그전까지 빈 회색 네모를 두느니 **어느 자리로 가야 하는지**를 보여줍니다. 종목의 기구 종류는
  6가지뿐이라 이미 그려 둔 기구 선화로 전부 덮입니다.
- **종목 이름을 15px로 키웠습니다.** 목록에서 제일 먼저 읽는 것이 이름인데 버튼보다 작았습니다.
- **줄마다 버튼 세 개(시연·사람 있어요·없어요)를 `⋯` 하나로 모았습니다.** 셋을 다 늘어놓으니
  정작 이름이 안 보였습니다.
- **워밍업**을 맨 위 한 줄로 뺐습니다. 종목이 아니라 준비입니다.

레이아웃 얼개(요약 카드 · 썸네일 · 이름 · 세트×중량×반복 · 줄 메뉴)는 피트니스 앱이 널리
쓰는 목록 패턴입니다. 색·여백·글자·그림은 전부 이 프로젝트의 것이고, 특정 앱의 화면이나
에셋을 가져오지 않았습니다.

### 오늘은 한 종목씩 (`app.js`)

종목 일곱 개가 한 화면에 깔려 있으면 **시작하기 전에 지칩니다.** 스크롤을 세 번 하다 보면
오늘 할 양이 얼마나 많은지만 보이고, 헬스장에서 실제로 필요한 건 "지금 이거" 하나입니다.

그래서 화면을 둘로 나눴습니다.

**시작 전** — 목록만 보여줍니다. 종목 이름과 `6세트 · 105kg · 6–10회` 한 줄. 세트 줄도, 워밍업도,
강도 기법도 없습니다. 여기서 정할 건 하나입니다: **오늘 얼마나 할 수 있는가.** 시간을 적으면
그 안에 들어오게 줄여 주고, 그다음 **시작하기**를 누릅니다. 이 버튼은 화면 아래에 고정돼 있어
스크롤과 상관없이 늘 보입니다 — 다음 행동이 하나뿐이어야 하는 자리입니다.

**시작 후** — 종목 하나만 보여줍니다. 위에 `1 / 4`과 진행 막대, 아래에 **다음 종목**.
남은 세트가 있어도 넘어갈 수 있게 뒀습니다(`다음 종목 (3세트 남음)`) — 기구가 막혀서 순서를
바꾸는 일은 헬스장에서 늘 있습니다. 다만 티는 냅니다. **목록** 버튼으로 언제든 전체로 돌아갑니다.

시간은 **분 단위로 직접 적습니다.** 30·45·60·90 칩은 빠른 선택일 뿐입니다 — "오늘은 37분밖에
없다"를 못 받으면 그 기능은 절반만 하는 것입니다. 빈 칸에는 오늘 예상 시간이 흐리게 떠 있어
몇 자리를 적는 칸인지 바로 압니다.

화면이 바뀔 때만 스크롤을 맨 위로 올립니다. 매번 올리면 RIR을 탭할 때마다 화면이 튀어서
못 씁니다.

### 시연은 직접 찍는다 (`prototype/demoClips.js`)

**근육이 칠해진 해부 렌더로는 초보자가 동작을 따라 할 수 없습니다.** 그건 "어디가 쓰이는가"를
말하지 "어떻게 하는가"를 말하지 않습니다. 초보자가 필요한 건 사람이 하는 걸 보는 것입니다.

경쟁 앱들이 쓰는 렌더는 라이선스 에셋입니다. 사려면 종목 수만큼 돈이 들고 재계약이 따라붙습니다.
**직접 찍으면 저작권이 이쪽에 있고, 한국 헬스장의 한국 기구가 나오고, 비용이 거의 안 듭니다.**

구조를 이렇게 잡았습니다.

- **한 개 찍으면 한 개가 바로 나옵니다.** `demoClips.js` 목록에 id를 적는 순간 그 종목만
  영상으로 바뀝니다. 83개를 다 찍을 때까지 출시를 미룰 이유가 없습니다.
- **안 찍은 종목은 지금의 동작 애니메이션이 그대로 돕니다.** 빈 칸이 생기지 않습니다.
- **정상 컷과 실수 컷을 전환합니다.** 초보자에게는 "이렇게 하세요"보다 "이러면 안 됩니다"가
  더 잘 박힙니다. 보여줄 실수는 앱에 이미 들어 있는 목록과 같은 것이라, 글과 영상이 어긋나지
  않습니다.
- **404를 찔러 보지 않습니다.** 있는지 없는지는 목록이 정합니다 — 헬스장 와이파이에서 영상 없는
  종목마다 실패 요청을 날리면 시연이 늦게 뜹니다.

찍는 순서는 추측하지 않고 엔진에 물었습니다. `tools/shotList.ts`가 설정 조합 **720판**을 돌려
종목별 처방 횟수를 세고, **관절 부하 0.7 이상**을 앞으로 뺍니다 — 영상이 급한 건 자주 나오는
것이 아니라 *모르면 다치는* 것이기 때문입니다. 빈도만으로 줄을 세우면 컨센트레이션 컬이 백
스쿼트보다 위로 옵니다.

```
1단계 17개 (관절 부하 0.7 이상) — 그중 13개가 랙에서 찍힌다. 삼각대를 거의 안 옮긴다
2단계 나머지 66개
```

규격·동선·법적으로 챙길 것은 `docs/촬영가이드.md`, 종목별 각도와 실수 목록은
`docs/촬영목록.md`에 있습니다(둘 다 생성물이 아니라 가이드는 손으로, 목록은 엔진이 만듭니다).

### 쓰는 근육 (`prototype/bodyMap.js`)

시연 화면 **맨 아래에** 정면·후면 인체와 근육 농도를 띄웁니다. 동작 → 수행 큐 → 흔한 실수 다음입니다 —
초보자가 먼저 필요한 건 "어떻게 하는가"이고, "어디에 오는가"는 그 다음입니다. 경쟁 앱들이 하는 것과 겉보기는 같지만
두 가지가 다릅니다.

**첫째, 그림을 직접 그립니다.** 해부학 자체는 저작물이 아니지만 특정 일러스트는 저작물입니다. 남의
렌더를 베끼거나 따라 그리지 않습니다.

**둘째, 종목별 그림이 없습니다.** 몸 하나와 근육 칸 14개가 있고, 색은 엔진의 `contribution`을 그대로
농도로 칠합니다. 종목이 83개든 830개든 그림은 한 장입니다. 그래서 이렇게 나옵니다.

```
컨벤셔널 데드리프트
  둔근 100% [주동근] · 햄스트링 90% [주동근] · 등 70% [주동근]
  승모근 50% · 전완 50% · 대퇴사두 30%
```

고정된 그림 한 장은 **둔근 100%와 대퇴사두 30%를 같은 색으로** 보여줍니다. 그건 사실과 다르고,
주간 볼륨이 쌓이는 방식과도 어긋납니다 — 우리 엔진은 이미 이 비율대로 부위별 유효 세트를 나눠
담고 있으므로, 화면도 같은 숫자를 보여주는 게 맞습니다. 주동근/협응근을 가르는 선은 0.7입니다.

정면에 7개, 후면에 7개로 갈라 뒀습니다. 한 근육이 양쪽에 칠해지면 "두 군데가 켜졌다"로 잘못
읽힙니다. 테스트가 이 균형과, 종목 83개가 쓰는 모든 근육에 칸이 있는지를 지킵니다.

### 쓰면서 고친다 (`gyms.ts`)

첫 화면에서 기구 31개를 정확히 고르게 할 수는 없습니다. 그래서 **운동하다 그 종목이 나왔을 때**
고칩니다 — 종목 옆의 **없어요** 버튼입니다. 그때는 눈앞에 기구가 있으니 틀릴 수가 없습니다.

"이 종목 빼기"가 아니라 **"이 기구 없음"**으로 받습니다. 종목만 빼면 같은 기구를 쓰는 다른 종목이
내일 또 나옵니다. 기구를 끄면 그 기구를 쓰는 종목이 전부 한 번에 정리됩니다.

누르기 전에 무엇이 사라지는지 보여주고, **언제든 헬스장 탭에서 다시 켤 수 있습니다.** 잘못 눌러서
종목이 사라지면 사용자는 앱을 못 믿습니다.

### 검색 먼저, 없으면 등록 (`gymPresets.ts`)

기구 31개를 체크박스로 고르게 하면 초보자는 거기서 앱을 닫습니다. 그런데 현장에서 보면 한국 헬스장은
몇 가지 유형으로 거의 다 덮입니다. **유형 하나만 고르면 기구의 대부분이 채워집니다.**

| 유형 | 기구 | 검색 |
| --- | --- | --- |
| 대형 · 프랜차이즈 | 31개 | 노출 |
| 동네 헬스장 | 21개 | 노출 |
| 크로스핏 박스 | 9개 | 노출 |
| 아파트 · 회사 · 호텔 | 11개 | **안 됨** |
| 홈짐 | 2개 | **안 됨** |

**아파트 커뮤니티 헬스장, 회사 헬스장, 홈짐은 검색에 안 나옵니다.** 나와서도 안 됩니다 — 주민이나
직원만 쓰는 곳을 지도에 올릴 이유가 없습니다. 그래서 `visibility: 'private'`으로 두고, 중복 판정에서도
남의 것과 비교하지 않습니다. 옆 동 사람의 홈짐이 후보로 뜨는 건 사생활 문제입니다.

등록 경로는 **검색 결과 아래에만** 둡니다. 먼저 찾아보게 만드는 것이 중복을 막는 가장 싼 방법입니다 —
대부분의 중복은 악의가 아니라 검색을 안 해봐서 생깁니다.

프리셋이 틀려도 괜찮게 설계했습니다. 실제로 그 종목이 처방됐을 때 "이 기구 없어요"를 누르면 그때
빠집니다. **첫 화면에서 전부 맞출 필요가 없습니다.**

### 중복 확인을 미루기 (`gyms.ts`)

등록 순간에 "혹시 이거 아닌가요?"로 막아 세우면 등록 자체를 포기합니다. 그래서 **나중에 확인**하는
길을 둡니다 — 후보를 `pendingMergeWith`에 적어두고 일단 쓰게 합니다.

그냥 버리면 영영 못 합치므로 반드시 적어둡니다. 그리고 **헬스장 탭에 왔을 때** 다시 묻습니다. 그때가
사용자가 헬스장을 생각하고 있는 순간이라 대답하기 쉽습니다.

합칠 때는 **사용자가 목록에서 고른 쪽의 이름으로 남습니다.** 기구는 최근 확인이 이기지만, 이름은
방금 지목한 것이 이깁니다. "다른 곳"으로 정리하면 둘 다 남기고 **같은 짝을 다시 묻지 않습니다.**

### 여러 곳을 다니는 사람 (`gyms.ts`)

세 곳 이상 다니는 사람은 드물지 않습니다. 평일은 회사 근처, 주말은 집 근처, 가끔 출장지.
매번 손으로 고르게 하면 잘못 고른 채로 운동하게 됩니다.

- `gymForWeekday()` — 요일별 기본 헬스장
- `suggestGymByLocation()` — 도착하면 알아서 그 헬스장으로. 내가 다니는 곳만 봅니다

### 기구 점유 (`occupancy.ts`)

헬스장에서 계획이 깨지는 가장 흔한 이유는 통증도 피로도 아닙니다. **스쿼트랙에 사람이 있는 것**입니다.
대부분의 앱은 이걸 모르는 척하고, 사용자는 앱을 끄고 아무거나 하게 됩니다.

판단 순서는 현장에서 하는 것과 같습니다.

1. **순서를 바꿉니다.** 대체하면 자극이 달라지지만, 같은 종목을 나중에 하면 잃는 게 없습니다.
2. 못 바꾸면(마지막 종목이거나 뒤 종목도 막혔으면) **대체**합니다.
3. 메인 복합 동작은 미룰 곳이 없으면 **기다리는 쪽**을 권합니다. 피로가 쌓인 뒤에 하면 그날 가장
   중요한 세트를 손해 보고 합니다. 다만 선택지는 같이 줍니다 — 아무것도 못 하게 하면 앱을 끕니다.

기구를 막는 단위가 중요합니다. **랙은 한 대가 여러 종목을 받습니다** — 막히면 바벨 스쿼트도 바벨 로우도
못 합니다. 반면 **레그프레스가 막혔다고 레그컬까지 못 하는 건 아닙니다.** 머신은 종목마다 다른 기계입니다.
이걸 구분하지 않으면 "머신이 막혔다"는 이유로 헬스장의 절반을 못 쓰는 것으로 계산합니다.

대체 후보는 자극 겹침(코사인 유사도) 50% 이상에서 고르되, **같은 동작 패턴을 앞세웁니다.** 레그컬 대신
스티프 레그 데드리프트를 하면 햄스트링은 겹치지만 하나는 무릎 굴곡이고 하나는 고관절 신전입니다.
보여주는 숫자는 손대지 않고 순서에서만 반영하고, 패턴이 다르면 "동작 결이 다름"이라고 적습니다.

### PWA · 알림 (`prototype/sw.js`)

엔진이 아무리 정확해도 헬스장에서 못 켜면 소용이 없습니다.

- **오프라인** — 셸을 캐시에 넣어두고 네트워크가 없으면 캐시에서 띄웁니다. 저장은 원래부터 로컬이
  원본(`storage.ts`)이라 지하에서도 그대로 돕니다.
- **휴식 알림** — 세트 사이에 폰을 주머니에 넣는 게 정상입니다. 알림을 페이지가 아니라 서비스 워커에서
  띄우는 이유입니다.
- **화면 유지** — 휴식 중에만 Wake Lock을 잡고 끝나면 놓습니다. 계속 잡고 있으면 배터리를 먹습니다.
- **시간 계산** — 남은 시간을 세지 않고 **끝나는 시각을 기억**합니다. 화면을 몇 분 잠갔다 열어도
  숫자가 틀리지 않습니다.

**애플워치 · 갤럭시워치.** 두 시계 모두 폰 알림을 손목에 미러링하므로 휴식 종료 알림이 그대로 갑니다.
갤럭시워치(Wear OS)에서는 "다음 세트 · +30초"를 손목에서 바로 누를 수 있고, 애플워치는 알림을 펼쳤을 때
보입니다. iOS는 **홈 화면에 추가한 뒤에만** 웹 알림이 열립니다(16.4 이상).

정직하게 말하면 한계가 있습니다. 폰 화면을 끈 채로 오래 두면 브라우저가 타이머를 재우기 때문에 알림이
늦거나 안 뜰 수 있습니다. **손목 알림을 100% 보장하는 방법은 서버가 예약 푸시를 보내는 것뿐**이고,
받는 쪽(`push` 핸들러)은 이미 열어뒀습니다. 손목에서 세트를 *기록*하려면 네이티브 워치 앱이 필요한데,
이건 PWA로는 되지 않습니다 — watchOS에는 브라우저가 없습니다.

### 통증 게이트 (`pain.ts`)

세션 생성 시 **통증 판정이 부하 계산보다 먼저** 적용됩니다. 순서를 바꾸면 아픈 관절에 어제보다 무거운 것을 얹게 됩니다.

| 통증 점수 | 관절 스트레스 0.6 이상 | 0.3 ~ 0.6 | 0.3 미만 |
|---|---|---|---|
| 7 ~ 10 | 중단 + 진료 권고 | 중단 + 진료 권고 | 수행 |
| 3 ~ 6 | 대체 운동 | 중량 90% | 수행 |
| 1 ~ 2 | 중량 90% | 수행 | 수행 |

대체 운동은 근육 기여도 코사인 유사도에서 통증 관절 부하를 뺀 점수로 고릅니다.
애매한 후보를 내놓느니 "대체 없음"을 반환합니다.

```
어깨 4점 → 바벨 오버헤드프레스 ✕ → 머신 숄더프레스 / 랜드마인 프레스
허리 4점 → 컨벤셔널 데드리프트 ✕ → 힙 쓰러스트 / 백 익스텐션 / 워킹 런지
```

대체 종목은 이력이 없어 중량을 정하지 않습니다. 다른 종목의 중량을 임의로 환산하는 것이 더 위험하므로, 원래 종목의 마지막 기록만 참고로 붙입니다.

## 동의와 개인정보 (`consent.ts`)

이 앱이 받는 것 중 **체중·통증·운동 기록은 건강에 관한 정보**입니다. 개인정보보호법은 이걸 민감정보로
보고 다른 동의와 묶지 말라고 합니다(제23조) — 이용약관에 끼워 넣고 한 번에 받으면 동의로 치지 않습니다.

그래서 세 가지를 지킵니다.

1. **민감정보는 따로 묻습니다.** "전체 동의" 버튼을 두지 않았습니다. 하나씩 읽고 하나씩 누릅니다
2. **필수와 선택을 가릅니다.** 선택을 거부해도 앱은 돌아갑니다 — 거부했다고 서비스를 막으면 그것도
   위법입니다(제22조)
3. **무엇을 왜 받고 얼마나 갖고 있으며 거부하면 어떻게 되는지** 먼저 말합니다

| 항목 | 구분 | 거부하면 |
| --- | --- | --- |
| 이용약관 | 필수 | 이용 불가 |
| 개인정보 (경력·성별·헬스장) | 필수 | 이용 불가 |
| **건강정보 (체중·운동 기록)** | 필수 · 민감 | 이용 불가 — 이 앱의 핵심입니다 |
| **통증 기록** | 선택 · 민감 | 통증에 따른 종목 대체만 꺼집니다 |
| 위치정보 | 선택 | 근처 찾기·자동 전환만 꺼집니다 |
| 마케팅 | 선택 | 안내만 안 옵니다 |

**동의가 실제로 동작을 바꿉니다.** 화면에서만 감추는 게 아닙니다 — 통증 동의가 없으면 `activePain()`이
빈 배열을 돌려주고, 위치 동의가 없으면 좌표를 아예 넘기지 않습니다(`myLocation()`).

**철회하면 데이터도 지웁니다.** 동의만 끄고 기록을 남기면 철회가 아닙니다. 필수 항목을 철회하면
서비스가 멈춘다는 것을 먼저 알리고, 확인하면 전부 지우고 처음으로 돌아갑니다.

**동의 문구에 판(version)이 있습니다.** 내용을 고치면 올리고, 올라가면 기존 사용자에게 다시 묻습니다 —
사용자는 이전 판에 동의했을 뿐 바뀐 내용에 동의한 적이 없습니다.

열람권(제35조)과 삭제 요구권(제36조)은 "어딘가 적혀 있다"로는 부족합니다. **체크인 탭 → 내 정보**에서
지금 바로 동의 현황을 보고, JSON으로 내려받고, 전부 지울 수 있습니다.

> 이 파일은 동의를 **받는 장치**이지 법률 자문이 아닙니다. 실제 출시 전에는 문구를 변호사에게
> 검토받아야 합니다.
